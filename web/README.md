# BENCH web app

Next.js 15 (App Router) + React 19 + TypeScript (strict). Plain CSS (global tokens in `src/app/globals.css`, CSS modules for the card, landing and sign-in screens). Light theme only. Product name is kept in one place: `src/lib/config.ts`.

## Look and brand

The app follows the BENCH site: Poppins (loaded with `next/font/google`), the tokens at the top of `src/app/globals.css` (`--orange`, `--blue`, `--green`, `--ink`, `--mute`, `--line`, `--surface-2`), pill buttons that turn blue on hover. The logo is the text wordmark in `src/components/Logo.tsx` (`Logo`, `Wordmark`); the company shows as "by" plus its logo (`ByLine`, `Lockup`), using `COMPANY_NAME`, `COMPANY_SHORT_NAME` and `COMPANY_LOGO` from `src/lib/config.ts`. Icons and e-mail logo are rebuilt from the Poppins font into `public/brand/` and `brand/`.

The signed-in app uses the whole window. Beside every editor (card editor, company brand page) `PreviewDock` keeps the live card in view (sticky panel on a laptop, a floating Preview button and full-screen sheet on a phone) and can open the card, as it is right now and unsaved, in a new tab (`/app/preview/[id]`, `/app/preview/brand`; the draft travels through `src/lib/preview-bridge.ts`). The public card page `/c/[code]` is one centred phone-width column (card, Save contact, area below, footer) on a page that fills the whole window in the card's own colour, with no box or frame around it.

The company brand page is a guided flow of six steps (Company, Colours, Logo, Artwork, Card style, Finish); the step and summary logic is in `src/lib/brand/steps.ts`.

## Setup

```
npm install
copy .env.example .env.local      (then edit if needed)
```

Environment (all optional, defaults shown in `.env.example`):

| Variable | Meaning |
| --- | --- |
| `NEXT_PUBLIC_API_URL` | API as the browser sees it (public card events, QR image, vCard). Default `http://localhost:8100/api/v1` |
| `API_URL` | API as the Next.js server sees it (server rendering, sign-in proxy) |
| `NEXT_PUBLIC_APP_NAME` | Product name, default `BENCH` |
| `NEXT_PUBLIC_PUBLIC_HOST` | Host shown in card addresses. Must be set to the real card domain before launch; the default `ilaf.one` is only a placeholder |
| `NEXT_PUBLIC_WEB_URL` | Public address of this app (canonical and Open Graph links) |
| `NEXT_PUBLIC_GOOGLE_CLIENT_ID` | Google OAuth client id (build-time). Empty hides the Continue with Google buttons |
| `CLIENT_IP_HEADER_SECRET` | Server only. Same value as in the backend `.env`; the web server signs the visitor address it sends to the API (`X-BENCH-Client-IP` and `-Signature`) so per-visitor limits work |
| `COMPANY_SUPPORT_EMAIL` | Server only. Contact address printed in `/privacy` and `/terms` (a visible placeholder shows when empty) |
| `LEGAL_DRAFT_BANNER` | Server only, default `true`: shows "Draft for legal review before launch" on `/privacy` and `/terms`. Set `false` only after a lawyer approved the texts |
| `INSECURE_COOKIES=1` | Only for running `next start` over plain http away from localhost |

## Design library

The faces, layouts and openings are drawn by a string engine (no DOM). The public page (`app/c/[code]/page.tsx`) runs it on the server and sends the finished card markup, so the card is in the first bytes of the page and fully visible with scripts off; the engine (about 470 KB) is not in the public page's browser bundle. The browser part is `components/card/CardBehaviour.tsx` (flip, tabs, link taps, Save contact, opening animation via the `go` class after load, long-name fitting). With scripts off, Save contact is a plain link to the contact file and layouts with tabs list the other tabs under the first one (the server adds them inside `<noscript>`, see `withoutScriptTabs` in `lib/library/render.ts`), so every button stays reachable. Accordion layouts use native `<details>`, which open without scripts. The editor and brand preview use `CardView`, which runs the engine in the browser so edits show at once. Everything under `src/lib/library/generated/` and `public/card-library/designs.css` is generated and committed. To rebuild it from the design page pieces (the folder with card_designs.html, app3.js, faces*.js, dv*.js, ops*.js and the css files):

```
npm run build:library -- <folder with the design page pieces>      (or set DESIGN_SRC)
```

The script is `scripts/build-design-library.mjs`; the hand-written parts are in `scripts/design-library/` (shared state, the 12 original layouts written for real links, the page renderer, extra CSS). The stylesheet is scoped under `.cfl` so it cannot touch the rest of the app. `CardMarkup` loads it with a style precedence, so it is in the head and blocks the first paint (no unstyled flash), and only pages that draw a card load it; the card fonts link comes after the card in the body so a slow font host never delays the card. `next.config.ts` serves `/card-library/*` with a one-year immutable cache; the address carries a content hash (`?v=`), which changes whenever the library is rebuilt.

### Brand colours below the card

The design switch "use brand colours" (`design.brand_colors`) works in all 400 layouts and for every button kind. `lib/library/chip.ts` holds the official colour of each kind (WhatsApp #25D366, LinkedIn #0A66C2, Facebook #1877F2, Instagram #E4405F and its gradient, X, TikTok, Medium, Threads #000000, YouTube #FF0000, GitHub #181717, Telegram #26A5E4, Snapchat #FFFC00 with a dark logo, and so on; a call is #34C759, email #EA4335, a website and booking #3B82F6, directions #34A853; a custom link without a brand shows the card's accent). Colours are never tinted to fit a palette: only when a colour would vanish against the page (black on a dark page, yellow on a light one) `brandChip` puts a plain light or dark chip behind the logo, which keeps its brand colour. `buildInput` hands the engine each button's `bc` (chip) and `bf` (logo) colours. In the first 12 layouts they are the `--mc` of the chip (`--mf` when the logo is not white or dark ink). The layouts after them draw with `--pacc` / `--pon`, so the engine (`brandTint` in `engine-tail.js`) puts `--bc`, `--bf`, `--pacc` and `--pon` on each button's own link element and everything inside follows. Layouts with no coloured area of their own get a fallback in `supplement.css` (a chip behind the logo, or a thick underline in the brand colour for typographic layouts); the layout numbers are listed in the comments there and must be recomputed if layouts are rebuilt. With the switch off nothing is added and every chip uses the card's accent.

### Font and text size

Two design settings change the text of the card face without touching the 400 face sources: `design.font` (a typeface for the name, title, role/company and contact lines) and `design.size` (60 to 150 percent for the same lines together). Rules, font list, safe scale and the pure fit logic are in `lib/library/text.ts`; the browser measuring is in `lib/library/textfit.ts`; the editor step is `components/editor/design/TextStep.tsx` (the wizard has six steps: Face, Colours, Text, Below the card, Animation, Finish; the company brand page and the department editor use the same wizard).

- **How it reaches the card.** `drawPage` puts the classes `tx-font` / `tx-size` and the variables `--tf` (font stack), `--tfa` (Arabic stack), `--ts` (scale in use) and `--tsr` (size asked for, percent) on the `.cfl` wrapper, and `CardMarkup` adds the small stylesheet `TEXT_CSS` (only for a card that uses one of them). The stylesheet sets `font-family` on `.n .t1 .t2 .co .cl .ln` and `zoom: var(--ts)` on the outermost of those blocks. `zoom` was chosen because the faces size their text in `cqw` per class (no variable can multiply those) and `transform: scale` would not change the room a block takes. A browser without `zoom` ignores the rule: the text stays at 100% and nothing breaks. Faces that set their own mono or pixel typeface keep it (`FONT_LOCKED_FACES`, checked against the face CSS by a test); the size still applies to them.
- **Never overlapping.** The server HTML applies `min(size, 100)%`. After mount (`enhance` and `settle` in `lib/library/enhance.ts`) `clampTextSize` draws the card on a hidden copy at the asked size and at 100%, runs the face's own long-name fitting on it, and accepts the size only if it adds no text-outside-the-face, text-on-text or text-on-photo problem that the face does not already have at 100%, and the face did not have to shrink the name or title further. An enlarged size is held to the largest that fits (never below 100%); a size below 100% that breaks a face (a block placed by its own offsets moves when it shrinks) moves up to the nearest size that works. The same code runs for the public page, the editor preview, the thumbnails and the new-tab preview. The size slider shows the largest size that fits (`useMaxFit`) and cannot be dragged past it.
- **Fonts.** The twelve Latin fonts and Cairo and Tajawal (Latin and Arabic subsets) are self-hosted by `scripts/copy-card-fonts.mjs` (add a family there to add a font; `@fontsource/cairo` and `@fontsource/tajawal` are exact-version dependencies). IBM Plex Sans Arabic is the app's own Arabic font (`--font-plex-ar`). When a Latin font is chosen, Arabic runs of the card use the Arabic font in `FONTS[].arabic`. To add a font: add it to `FONTS` here and to `FONT_KEYS` in `backend/ilaf/design.py`, and to the script's list; the tests compare all three.
- **Checks.** `lib/library/text.test.ts` covers the key lists, the font stacks, the fixed-typeface list, the fit rule and a clamp run over ten people, forty faces and three sizes on synthetic boxes. The real layout was checked in headless Chrome: forty faces (every tenth) at 60, 100 and 150% with four people (short and long English, two Arabic) counted the text problems that the size adds over the same face at 100%, once with the size applied as asked (with and without the faces' own fitting) and once after the clamp; after the clamp the count is 0 (also with Dancing Script, Cairo, Bebas Neue and Playfair Display). Firefox and Safari were not run: both support `zoom`; a browser that does not simply keeps 100%.

### Page colour

The page behind the card is not the card's second background any more. `lib/library/page.ts` derives it so the card stands out: a dark card sits on a lighter tint of itself (about 16 points of lightness up, hue kept, a little less saturated), a light card on a darker tint (about 10 points down), and a mid-tone or vivid card (orange, yellow) on a deep or pale neutral, at least 1.5 : 1 in luminance from the card (1.2 : 1 for a light card, which is bright on bright). Text on the page stays 4.5 : 1 and the button colour 3 : 1; the text on a button is kept as the colourway has it when it reads. The same function gives the card edge (`--pgline` hairline and `--pgsh` soft shadow) that `supplement.css` puts on every card face. `resolveColours`, `buildInput` (the engine returns what it is given as `page`) and the company palette all use it, so the public page, the editor preview and the preview dock show the same page colour.

## Company brand

Company workspaces carry a palette, logo options and artwork (see "Company branding" in the API contract). Design colour 4 means the company colours; without a palette it renders as colourway 0. The pure logic is in `src/lib/library/company/`: `colour.ts` (palette from two brand colours, contrast guarantee), `marks.ts` (full logo, symbol, symbol with name, monogram; corner, chip and size decisions), `artwork.ts` (sample backgrounds, colour layer, logo pattern, template zones A-D), `brand.ts` (API brand to render shape, defaults), `compose.ts` (lays the brand on the engine markup, server-safe). The server measures the pictures with `sharp` when available (`src/lib/server/brand-info.ts`, also behind `/api/brand-info` for the editor); without it cards fall back to safe defaults. The browser then refines the logo corner and background edge from the real face (`lib/library/enhance.ts`); with scripts off the logo shows above the card and the card is fully readable. The engine accepts a company palette (`palette` on its input); the same change is in `scripts/design-library/engine-tail.js` and the generated `engine.js`, so rebuild keeps it. Brand page: `app/app/brand/page.tsx` and `components/brand/`. `PUBLIC_CARD_REVALIDATE` sets how long the server keeps a public card (default 15 s).

## How sign-in works

Tokens never reach page scripts. `/api/session/*` talks to the API and stores the tokens in httpOnly cookies. The browser calls `/api/proxy/*`, which adds the token and refreshes it once when it has expired. `src/middleware.ts` sends signed-out visitors away from `/app/*`.

## Deploy

`npm run build` then `npm start` (port 3100) behind a reverse proxy with HTTPS, with `API_URL`, `NEXT_PUBLIC_API_URL`, `NEXT_PUBLIC_WEB_URL` set at build time for the public values. The server needs Node 20+ and its `node_modules` (the logo list is read from the `simple-icons` package on the server). Add the web origin to the backend `CORS_ALLOWED_ORIGINS`; the public endpoints must allow any origin because visitors' browsers post card events to the API directly.

## Card features and tools

Contact forms on the public card (`app/c/[code]/ExchangeDialogs.tsx`): "Share your details" (owner-set fields, consent line with a privacy link, honeypot, time check, "Also save <name>'s contact" download and a success screen with a Save contact button) and "Request a meeting" (up to three free-text times). Owner settings are in the editor Profile tab (`components/editor/ExchangePanel.tsx`); the privacy address and "e-mail company admins" switch are in Settings (`components/app/LeadSettingsPanel.tsx`). The Meeting button (`lib/card/meeting.ts`) is either an https booking link (Calendly, Google Calendar, Cal.com, Microsoft Bookings, any https) with an automatic logo, or the built-in form. Its kind is listed in `EXTRA_PLATFORMS` of `lib/card/catalogue.ts`, not in `PLATFORMS`, because the brand-colour tables under `lib/library` are checked against `PLATFORMS`; without a recognised provider the button uses the card accent. To give it a fixed brand colour, add `Meeting` to `KIND_COLOURS` in `lib/library/chip.ts` and move it into `PLATFORMS`.

Tools group in the sidebar (all use the chosen card's colours and the company logo, see `components/app/ToolCard.tsx`):
- `/app/signature`: four e-mail signature styles (`lib/tools/signature.ts`), table-based inline-styled HTML with absolute https pictures, a checker (`emailHtmlProblems`) that the tests run on every style and option, Copy signature (HTML plus text on the clipboard), Copy HTML source, Copy plain text. The QR picture is `GET /public/cards/<code>/qr.png`. Pictures only load in mail once the API and media are on public https addresses.
- `/app/background`: a 1920x1080 PNG drawn in the browser on a canvas (`lib/tools/background.ts`), six layouts that keep the middle "person zone" clear, brand/dark/light and a soft variant. A company logo is drawn only if the media host sends `Access-Control-Allow-Origin` (the API does for `/media/`; give an S3 bucket the same rule), otherwise the picture is made without it.
- `/app/scan`: paper card scanner. `lib/scan/parse.ts` turns text into fields with confidence hints (20 sample cards in `parse.test.ts`); `lib/scan/ocr.ts` loads tesseract.js (pinned 7.0.0) lazily, only on this page, from `public/ocr`. The worker, the three LSTM engine builds and the English and Arabic language files are copied there by `scripts/copy-ocr.mjs` (runs as `prebuild`, or `npm run copy:ocr`); nothing comes from a CDN. If the files are missing the page says so and offers pasted text. Actions: vCard download, a lead (`source: scanned_card`), and, with `?card=<id>` (the editor's "Fill from a paper card"), a confirm dialog that fills name, title, company, mobile and e-mail.
- `/app/qr`: a switch between "Link to my card" and "Contact inside the QR" (`lib/card/qr-vcard.ts`: a small vCard 3.0 that works offline, address and note only on request and cut first when the payload passes 320 bytes; a warning above 250 bytes). PNG and SVG downloads for both.

Public page weight (measured on the scratch build, sample card with photo): HTML 50 KB, 14.5 KB gzipped, card fully drawn on the server so it shows without scripts; the page's browser scripts are about 159 KB first load and are not needed to see the card; the web font stylesheet is linked after the card. The contact file endpoint answers about 2.9 KB (mostly the 256 px photo), the QR PNG about 0.5 KB.

## User guide: checklist, tours, prompts and help centre

Everything a new user is shown is data plus a few small components. The pure logic is in `src/lib/guide/` (tested without a browser), the screens are in `src/components/guide/`, the articles are in `content/help/`. Texts are in the `guide` and `help` areas of `src/lib/i18n` (English first, then Arabic).

- **Guides and steps** (`lib/guide/guides.ts`): one guide per audience (`personal`, `company_owner`, `company_admin`, `employee`), each an ordered list of steps `{id, title, text, route, doneWhen, appliesWhen?, optional?, focus?}`. `doneWhen` is a small declarative condition on the guide context (`{is: "has_photo"}`, `{gte: ["items_count", 2]}`, `{all: [...]}`, `{any: [...]}`, `{not: ...}`). `route` may contain `{card}` (the person's card id). `focus` says what to highlight when the person arrives from the step (`/page?guide=<step id>`). To add a step: add it to the guide, add its title and text keys (`guide.step.<id>.title` and `.text`) in `en/guide.ts` and `ar/guide.ts`, add its id to `FOLLOW_UPS` in `whatnext.ts`, and, if it needs a new fact, add a field to `GuideContext` (`types.ts`), fill it in `context.ts` and add a test.
- **Context** (`lib/guide/context.ts`): `buildContext` turns data the app already loads (cards, company brand, members, contacts count, departments, webhooks, field rules) plus saved flags into plain facts. Nothing new is requested from the API except the guide progress. `useGuideState` (`lib/guide/hooks.ts`) wires the queries.
- **Progress** (`lib/guide/engine.ts`, `lib/guide/api.ts`): `GET` and `PUT /api/v1/guide/progress` (see `API_CONTRACT.md`). A step is done when the data says so, or when the person marked it; skipped steps count as finished. Pages tell the guide about events with `announce("card_published")` (also `first_invite_sent`, `brand_saved`, `first_lead`, `export_done`) and `announceFlag("signature_copied")`, which are window events, so a page never imports the guide.
- **Welcome** (`Welcome.tsx`): up to three screens, shown once to an account younger than 14 days (`GuideRoot.tsx`), replayable from the Help menu. People whose role says it all (company owner, admin, employee) skip the question.
- **Checklist** (`GettingStarted.tsx`): on the home page; employees have no home page, so it sits at the top of their cards page.
- **What next** (`whatnext.ts`): `PROMPTS` are the one-time prompts after a key event; `SUGGESTIONS` and `FOLLOW_UPS` decide what to offer after a step; `ALL_DONE` is the list shown when a guide is complete.
- **Page tours** (`tours.ts`, `Tour.tsx`, `position.ts`): a tour is `{id, route, prefix?, title, tips: [{target, title, text, openFirst?}]}` with 3 to 6 tips. `target` is a selector, normally `[data-guide="name"]`; add that attribute to the element in the page, add the tour and its texts (`guide.tour.<tour>.<tip>.title` and `.text`), and put `<TourButton />` next to the page title. A tip with no element on screen is skipped; `openFirst` clicks a tab before measuring. Placement maths is in `position.ts`.
- **Empty states**: `EmptyState` (title, text, one action, an optional "Learn more" link to a help article by slug).
- **Help centre** (`/app/help`, `/app/help/<slug>`): Markdown files `content/help/<language>/<slug>.md` with a header (`title`, `summary`, `audience`, `pages`, `related`, `updated`). The same slugs must exist in every language (a test checks it, the header values, internal links and that every page named in `pages` exists in `lib/help/pages.ts`). Body: `##` and `###` headings, paragraphs, `-` bullets, `1.` steps, `>` tips, `**bold**`, `[text](/app/page)`; `{{APP}}` becomes the product name. Search (`lib/help/search.ts`) ignores Arabic marks and letter shapes. The thumbs are saved as `help/<slug>` progress. Contact support is a disabled "Coming soon" until `SUPPORT_ROUTE_READY` in `lib/help/config.ts` is set to true.
- **Adding an article**: write `content/help/en/<slug>.md` and `content/help/ar/<slug>.md`, run `npx vitest run src/lib/help`.

## Languages (English and Arabic, right to left)

English is the source language and the default. Arabic (`ar`) is the first translation; the system is built for more.

**How the language of a visit is chosen** (`src/lib/i18n/config.ts`, `pickLocale`): the language saved on the account, then the `bench_lang` cookie (it mirrors the account: signing in copies the account's language into the cookie, the switcher writes both), then the browser's `Accept-Language`, then English. A card page uses the card's own `language` (`en`, `ar`, or `auto` = the visitor's). Digits are Western (0-9) unless the `bench_digits` cookie says `arab` (switch in Settings); dates are Gregorian.

**Where things are**

**Rules for code**
- Never write a user-facing text in a component: add the key to `en/<area>.ts` first, then `ar/<area>.ts`, and use `t("area.key", { values })`. A key chosen at run time is wrapped in `tk("area.key")`.
- `src/lib/i18n/i18n.test.ts` fails on a missing or extra key in any language, on different placeholders, on Arabic plurals without all six forms, on keys nobody uses and on keys used in code that do not exist. TypeScript checks the key sets too.
- **No raw server text.** A page never shows `error.message` or any sentence the API sent. It calls `apiErrorText(error, t, "area.fallbackKey")` (or `apiFieldText`, `apiFirstFieldText`, `apiReasonText`, `apiServerText`) from `@/lib/i18n/api-error` (hooks in `use-api-error.ts`). The text comes from `apiError.<code>` in `en/apiError.ts` and `ar/apiError.ts` (that area is shipped to every page). A code with no text uses the fallback key, then, only on an English screen, the server's English sentence; an Arabic screen never shows English from the server (it shows the fallback or `apiError.generic`). Codes that share many sentences (`validation_error`, `forbidden`, `not_found`, `plan_limit`, ...) show the server's own sentence when it is already in the page's language (the API translates by `X-Language`). `static-scan.test.ts` fails when a file reads `ApiError.message` outside the helper and when JSX text, visible props (`placeholder`, `aria-label`, `title`, `alt`, `label`), `toast("...")` or metadata hold English prose; mark a reviewed line with `// i18n-ok` or add a brand or technical word to the lists in that test.
- **Add an error code.** Raise it in the backend (`ApiError("my_code", "Plain English.", 409)`), run `python scripts/extract_error_codes.py` in `backend/`, add `"apiError.my_code"` to `en/apiError.ts` and `ar/apiError.ts`, and add the Arabic of the sentence to `backend/ilaf/locale_ar_errors.py`. `backend/tests/test_error_codes.py` fails until the registry, both web texts and the server Arabic exist.
- Numbers and dates go through `useI18n()` (`number`, `date`, `money`, ...), never `toLocaleString("en-GB")`.
- CSS uses logical properties only (`margin-inline`, `inset-inline-start`, `text-align: start`). Icons that point somewhere (`chev`, `arrow`, `logout`) mirror by themselves; others (phone, search) never do. Text typed by people (names, titles, companies, addresses, notes) gets `dir="auto"`; e-mail addresses, links and phone numbers get the class `ltr`.

**Cards in Arabic.** The 400 faces and layouts are drawn left to right and are not mirrored. The renderer marks every Arabic run (`<span class="ar" dir="rtl">`): it gets the Arabic font (IBM Plex Sans Arabic through `next/font`, with system fallbacks), no letter spacing and more line height; a block that is entirely Arabic is aligned to the right where its box left-aligned text (`alignArabic` in `lib/library/enhance.ts`); the fixed words of the engine and a list of decorative design words are swapped for the card's language. Words printed by an individual design that are not in `chrome-words.ts` stay English.

**Add a language** (for example French `fr`): 1) add `"fr"` to `LOCALES` and `LOCALE_NAMES` in `config.ts` (and to `RTL_LOCALES` if it is right to left); 2) create `src/lib/i18n/fr/<area>.ts` for every area (copy `ar/` and translate; the compiler lists what is missing) and add `fr` to `CATALOGUES` in `messages.ts`; 3) add `fr` to `CARD_TEXTS` in `lib/card/labels.ts` (and a word list in `chrome-words.ts` if wanted); 4) add the language to the backend (see backend README, "Languages"), the API's `SUPPORTED_LANGUAGES`; 5) `npx vitest run src/lib/i18n` until green.

## Security, privacy and self-hosting (production hardening)

- **Visitor address.** `src/lib/server/client-ip.ts` builds `X-BENCH-Client-IP` (+ HMAC signature) from the last `X-Forwarded-For` entry nginx wrote (fallback `X-Real-IP`, IP syntax validated, IPv6 in short form). The session route and the proxy route send it on every call; X-BENCH headers sent by a browser are dropped. Public card and directory pages are cached by Next (`PUBLIC_CARD_REVALIDATE`), so a per-visitor header would be wrong there: they do not send it, and `THROTTLE_RATES_JSON` must stay raised on the API for those reads (PRODUCTION_READINESS.md 9.1).
- **Origin check.** POST/PUT/PATCH/DELETE to `/api/session/*` and `/api/proxy/*` need an `Origin` (or `Referer`) whose host is the request's own host or the host of `NEXT_PUBLIC_WEB_URL` (www variants allowed); otherwise 403 `origin_refused`. GET/HEAD are unaffected. Code: `src/lib/server/origin.ts`.
- **Sessions.** Sign out calls `auth/logout` (refresh token revoked) and always clears the cookies. Change password stores the new `{access, refresh}` in the cookies (proxy route). Settings, Sign-in methods has "Sign out of all devices" (`auth/logout-all`).
- **Re-authentication.** `ReauthDialog` (`components/account/ReauthDialog.tsx`, hook `useReauth`) answers 403 `reauth_required` for Google link/unlink, set password, data export and download link: it asks for the password (or a fresh Google sign-in) and repeats the call with it.
- **Tokens out of URLs.** Invite lookup/accept and the data-download check/download use the POST-body API routes; the page URLs (`/join/<token>`, `/data-download/<token>`) are unchanged. The export ZIP is saved from a POST answer.
- **Throttling.** A 429 shows "Please wait N seconds", remembers the wait (`src/lib/throttle.ts`), refuses further changes from the browser until it ends, switches off the sign-in forms and the webhook test button, and shows a note with the countdown.
- **Closed companies.** A company scheduled for deletion answers 403 `workspace_pending_deletion`: non-owners get a blocking page, the owner a banner with Restore and Download contacts (`components/app/ClosedCompany.tsx`).
- **Pictures** are PNG, JPG or WebP only (`src/lib/images.ts`, message "Use a PNG, JPG or WebP image.").
- **Card fonts are self-hosted.** `scripts/copy-card-fonts.mjs` (runs in `prebuild`, or `npm run copy:fonts`) copies the latin woff2 files of 23 pinned `@fontsource/*` packages into `public/card-fonts`, writes `fonts.css` (`font-display: swap`, one `@font-face` per weight, fetched lazily) and `src/lib/library/generated/fonts.ts`. `next.config.ts` caches `/card-fonts/*` for a year. Nothing on a public card page is requested from a third party (checked with a headless Chrome network log). To add a font: install its `@fontsource` package, add a line to `FAMILIES` in the script. Latin only: characters outside Latin-1 fall back to a system font. The app's own fonts come from `next/font` (downloaded at build time, served from `/_next/static`); that build step needs access to Google and can fail on a bad network: run the build again.
- **Privacy policy and terms.** `/privacy` and `/terms` (server-rendered, English and Arabic, linked from sign-in pages, Settings and the public card footer). The texts are Markdown files in `web/content/legal/` (`privacy.en.md`, `privacy.ar.md`, `terms.en.md`, `terms.ar.md`); a lawyer replaces them and restarts the app. `{{COMPANY_NAME}}`, `{{APP_NAME}}`, `{{SUPPORT_EMAIL}}` are filled in; `%%` lines are editor notes; text in [square brackets] must be replaced. They are DRAFTS and carry a visible banner until `LEGAL_DRAFT_BANNER=false`. The exchange-contact form shows a short notice linking to the card owner's privacy link or `/privacy`.
- **Cookies.** Only the two httpOnly sign-in cookies (signed-in people only) and the language and number-style preference cookies are set; there are no analytics, advertising or tracking cookies or scripts, and no third-party fonts, so no cookie banner is shown. Google's sign-in script (and its cookies) loads only when a page shows the Continue with Google button. Add a banner and consent before introducing any analytics or ads, and have counsel confirm the language cookie needs no consent in the target markets.
