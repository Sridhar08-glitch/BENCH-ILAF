# BENCH production readiness review

Scope: `backend/` (Django 5.2 + DRF), `web/` (Next.js 15), plus how they will run on the Contabo VPS next to the other app.
Method: read-only code review of every view in every backend app (accounts, billing, cards, public, privacy, wallet, workspaces, operations,
leads, analytics), settings, middleware, throttles, image and link tools, webhook sender, emails, the web route handlers, session handling, cookies,
next config and five pages; `npm audit` and `pip-audit` against the lock/requirements files; `manage.py check --deploy`; the full backend test suite.
Nothing was run on a real server, PostgreSQL, a real mail server or a real browser: see "Not verified" at the end.

Evidence is `file:line` relative to `C:\hope\Cardfolio`. Severity words: CRITICAL (exploitable now, serious), HIGH, MEDIUM, LOW, INFO.

## 1. Verdict

The product code is in good shape for a first launch: object ownership checks are consistent (no cross-account data access found in any view),
there is no mass-assignment hole, uploads are re-encoded and SVG is refused, outgoing link fetching and webhooks have real SSRF defences, e-mail text is escaped,
passwords are hashed, tokens rotate, exports are private and single-use, and 555 backend tests passed at the time of the review (773 now). The deployment files in this folder are complete.

What is **not** ready: the rate limits do not work behind the website server (B1), nothing has ever run on PostgreSQL or Linux (B2), the legal pages and the
Google Fonts dependency need work before real customers (B3), e-mail is not set up (B4), and a few hardening gaps remain in uploads, webhooks, token revocation
and one privacy lock (B5 to B9).

## 3. BLOCKERS (fix before real customers)

### B1. Rate limits and visitor identity do not work behind the website server. HIGH
- Evidence: `web/src/app/api/session/[action]/route.ts:10-16` (login, register, Google, invite accept) and `web/src/app/api/proxy/[...path]/route.ts:43-45` (forgot, reset, slug check, every signed-in call) and `web/src/lib/public-api.ts:8,23` (server-side render of every public card and directory) call the API from the Next.js server without forwarding the visitor's address. The API's `client_ip()` (`backend/ilaf/utils.py:42-52`) therefore sees one address (127.0.0.1) for all visitors.
- Effect: every IP throttle (`backend/ilaf/settings.py:200-214`) becomes ONE shared counter for the whole world. `auth_login` is 20/min in total: an attacker sending 20 bad logins a minute locks everybody out; ordinary growth does the same. `public_read` is 240/min in total: past that, public card pages fail to render (429) for everyone. Brute-force protection per attacker does not exist.
- Interim (already delivered): `THROTTLE_RATES_JSON` in `env.production.example` raises the shared limits; nginx limits each visitor's sign-in calls (`bench-web.conf`, `/api/session/`) at 10 per minute per address before they reach the web app. This stops a flood but cannot give per-user limits for forgot/reset/register.
- Fix (small, web code, three call sites): read the incoming `x-forwarded-for` (nginx sets it to the real address) with `headers()` in the route handlers and the server fetch helpers, and send it as `X-Forwarded-For` to the API. Then in `client_ip()` (backend): trust forwarded headers only when `REMOTE_ADDR` is a loopback/trusted proxy, validate with `ipaddress.ip_address()`, fall back to `REMOTE_ADDR`, and ignore `CF-Connecting-IP` unless Cloudflare is really in front (the nginx files already strip it). Then delete `THROTTLE_RATES_JSON` from the `.env`.
- Related: finding H1 below (header forgery) and the unthrottled authenticated API (R3).
- **Status: backend DONE, web half still to do.** `client_ip()` now trusts forwarded headers only when the TCP peer is in `TRUSTED_PROXY_IPS` (default loopback), reads `X-Forwarded-For` from the right (skipping trusted proxies and `NUM_PROXIES` extra hops, garbled entries ignored), validates every address with `ipaddress`, ignores `CF-Connecting-IP` unless `TRUST_CLOUDFLARE_HEADER=true`, and accepts a new header `X-BENCH-Client-IP` (optionally signed with `X-BENCH-Client-IP-Signature`, HMAC-SHA256 of the address with `CLIENT_IP_HEADER_SECRET`) from the web server. IPv6 visitors are throttled per /64. Files: `backend/ilaf/utils.py`, `backend/ilaf/throttles.py`, `backend/ilaf/settings.py`; tests `tests/test_client_ip.py`, `tests/test_user_throttles.py` (class `AddressThrottleTests`). Exact web change and nginx lines: section 9. **Web half DONE:** `web/src/lib/server/client-ip.ts` (`visitorHeaders`), used by the session route (login, register, Google, restore, accept-invite) and the proxy route (forgot, reset, every signed-in call); verified on a real stack (the backend logged the forwarded address; a forged or unsigned header is ignored). Public card and directory pages are cached by Next, so they follow 9.1 and do NOT send it: keep `THROTTLE_RATES_JSON` raised for server-rendered reads, delete it only if those pages become uncached. Tests `web/src/lib/server/client-ip.test.ts`, `web/src/app/api/routes.test.ts`. Delete `THROTTLE_RATES_JSON` from the `.env` only after the web change is live (server-rendered public card reads still share one address until then).

Load the Google sign-in script only after the user presses the button.
- **Status: DONE in code (legal text needs a lawyer).** Fonts: 23 families self-hosted (`web/scripts/copy-card-fonts.mjs`, `public/card-fonts`, `@fontsource/*` pinned 5.3.0, latin woff2, `font-display: swap`, immutable cache in `next.config.ts` and `bench-web.conf`; Google hosts removed from the CSP); a headless-Chrome network log of a public card page shows zero third-party requests. ### B4. E-mail is not set up. HIGH (operations)
- Evidence: without `EMAIL_HOST` the backend uses the console backend (`backend/ilaf/settings.py:251`): password reset, invites, lead notifications, export links and weekly reports are printed to the log and never delivered. The sender `no-reply@ilaf.qa` is the default (`:241`).
- Fix: use a transactional provider over port 587 (not the VPS itself; Contabo blocks port 25). The DNS work for `ilaf.qa` (owner): SPF record that includes the provider; DKIM records the provider gives you; DMARC `_dmarc.ilaf.qa TXT "v=DMARC1; p=none; rua=mailto:dmarc@ilaf.qa"` for two weeks, then `p=quarantine`; make the From domain match the authenticated domain; add a monitored reply address instead of no-reply for lead alerts; send a test to Gmail and Outlook and check "Show original" says SPF, DKIM and DMARC pass; add a `List-Unsubscribe` header to the weekly reports. `check_bench.sh` reports `EMAIL_HOST is empty` as a failure.
- Also: e-mail addresses are never verified at registration (`email_verified` stays false, `backend/accounts/views.py:34`); decide if sign-up should require a confirmation link (it reduces spam accounts and the "pre-registered victim address" problem, finding L8).
- **Status: OPEN (owner, DNS and SMTP).** Backend part done: password-reset mail is now sent after the answer is ready (`EMAIL_AFTER_RESPONSE`, default on), so a slow mail server no longer slows or reveals anything on forgot-password.

### B5. Uploads: Pillow may open any image format and the pixel limit only warns. MEDIUM/HIGH
- Evidence: `backend/ilaf/images.py:14-28` (`_open` is called with `allowed_formats=None` at `:44` and `:53`), `:75-81` (`icon_from_bytes` handles bytes fetched from a remote website). `Image.open()` without `formats=` also parses EPS, PDF-like and other formats; EPS can invoke Ghostscript if it is installed. `Image.MAX_IMAGE_PIXELS` only raises a warning at 40 MP (error at 80 MP, about 320 MB of RAM per upload on a 1.5 GB-limited service).
- Fix: `Image.open(f, formats=["PNG","JPEG","WEBP","GIF"])` in all three places; check `width*height` against an explicit limit before `load()`; turn `DecompressionBombWarning` into an error (`warnings.simplefilter("error", Image.DecompressionBombWarning)`); do not install Ghostscript on the server.
- **Status: DONE** (stricter than the fix above: GIF is refused too). Every upload and favicon goes through `decode_safely` in `backend/ilaf/images.py`: first bytes must be JPEG, PNG or WebP (extension and content type are ignored), `Image.open(..., formats=[that one format])`, animated files refused, header size checked before decoding (`IMAGE_MAX_PIXELS`, default 40 million, and 12000 px per side), `DecompressionBombWarning` is an error, and corrupt files give one plain message. Favicons fetched from websites also accept a classic `.ico` (the usual `/favicon.ico`), nothing else. Stored file names now carry 32 random hex characters. Tests `tests/test_image_uploads.py`. Still do not install Ghostscript.

### B6. One slow or broken webhook receiver stalls every company's webhooks. MEDIUM/HIGH
- Evidence: `backend/leads/webhooks.py:127-141` (the 5 s timeout is per socket read, not total; a receiver that sends a byte every 4 s holds the sender for over an hour), `:317-346` (`process_queue` sends one after another and has no `try/except` around `attempt()`: one unexpected error aborts the run and leaves the row locked; the 120 s lock then expires and the delivery is re-sent), `backend/leads/webhook_views.py:133-140` (the "Send test" button sends synchronously inside a web request; any free account can create a company and call it).
- Fix: total deadline with chunked reads; wrap each `attempt()` in `try/except`, mark failed and clear the lock; throttle the test button (5/min per endpoint) or run it in the queue; apply a per-run time budget. Catch `ValueError/UnicodeError` in `split_url`/`resolve_host` (`:75-99`, otherwise a crafted URL gives a 500).
- **Status: DONE.** `backend/leads/webhooks.py`: connect limit 3 s and a total deadline of 8 s enforced by a watchdog that shuts the socket (also when the receiver says `Connection: close` and trickles the body); `process_queue` takes deliveries round-robin per endpoint (5 per endpoint per run, oldest-waiting endpoint first), stops an endpoint for the rest of the run after a timeout or 15 s of its time, stops the whole run after 50 s, records unexpected errors on the delivery and always clears the lock (lock 60 s); the test button is limited to 5 per minute per endpoint (429); crafted URLs give a plain refusal instead of a 500; `WEBHOOK_ALLOW_PRIVATE_TARGETS` from the environment counts only while `DEBUG` is on (R14); NAT64, 6to4 and IPv4-compatible ranges are refused (R16, shared helper `backend/ilaf/netsafety.py`, also used by the link fetcher). Tests `tests/test_webhook_fairness.py`.

### B7. Password reset and change do not sign out other sessions. MEDIUM/HIGH
- Evidence: `backend/accounts/views.py:183-190` (reset) and `:193-201` (change). Refresh tokens live 30 days (`backend/ilaf/settings.py:192`); the blacklist app is installed but never used on these paths. A stolen refresh token survives a password reset.
- Fix: after `set_password`, blacklist the user's `OutstandingToken` rows (the privacy code already does this when purging) and, for change-password, return fresh tokens. Also invalidate older reset tokens when a new one is issued (`:148-164`).
- **Status: DONE** (access tokens already issued still work until they expire, at most 60 minutes; they cannot be revoked without a per-request database check). Refresh tokens are now blacklisted on password reset, on change-password (the answer is now `200 {access, refresh}` with fresh tokens for the current device), on the new `POST auth/logout-all`, when an account deletion is requested, and when a member is removed, suspended or demoted from admin. New `POST auth/logout` revokes one refresh token. Only the newest reset link works. Files: `backend/accounts/services.py` (`revoke_refresh_tokens`), `accounts/views.py`, `operations/actions.py`, `privacy/services.py`; tests `tests/test_session_revocation.py`.

### B8. Pending-deletion lock is bypassed on lead endpoints. MEDIUM (privacy)
- Evidence: `backend/leads/views.py:229-239` (`_open_lead`) never calls `refuse_if_pending_deletion` (compare `backend/workspaces/access.py:23,53`). Employees/admins of a company that asked for deletion can still read lead personal data.
- Fix: call `refuse_if_pending_deletion(member)` in `_open_lead` and in the invite-accept view.
- **Status: DONE** (stricter: while a company waits to be deleted nobody reads or changes its contacts, the owner may only download the spreadsheet; webhooks stop sending and their delivery log is closed; invites to it are dead). Code: `lead_access` and `_open_lead` in `backend/leads/views.py`, `InviteLookupView.get_member`, `webhooks._due_filter`. Tests `tests/test_lead_lock.py`.

### 9.1 Web change for B1 (three call sites) and nginx

The API reads the visitor address from `X-BENCH-Client-IP` when the call comes from a trusted proxy (loopback by default). Add one helper and use it in the three places that call the API on behalf of a visitor.

New file `web/src/lib/server/client-ip.ts`:

```ts
import { headers } from "next/headers";
import { createHmac } from "node:crypto";

// nginx (bench-web.conf) overwrites X-Forwarded-For with the address it saw, so the last entry is the visitor.
export async function visitorHeaders(): Promise<Record<string, string>> {
  const h = await headers();
  const raw = (h.get("x-forwarded-for") || "").split(",").pop()?.trim() || h.get("x-real-ip") || "";
  if (!raw) return {};
  const out: Record<string, string> = { "X-BENCH-Client-IP": raw };
  const secret = process.env.CLIENT_IP_HEADER_SECRET;
  if (secret) out["X-BENCH-Client-IP-Signature"] = createHmac("sha256", secret).update(raw).digest("hex");
  return out;
}
```

The three call sites (add `...(await visitorHeaders())` to the headers of the `fetch` to the API):
1. `web/src/app/api/session/[action]/route.ts:10-16` (login, register, Google, invite accept).
2. `web/src/app/api/proxy/[...path]/route.ts:43-45` (forgot, reset, slug check and every signed-in call). The proxy must forward only this header, never a client-supplied `X-BENCH-*` header.
3. `web/src/lib/public-api.ts:8,23` (server-side render of public cards and the directory). Reading `headers()` makes that page dynamic. If the public card pages are cached or static, skip this call site and keep `public_read` and `public_directory` raised in `THROTTLE_RATES_JSON` for server-rendered reads (nginx already limits each visitor in front).

Environment: put the same random value in `CLIENT_IP_HEADER_SECRET` in the backend `.env` and the web `.env`. Then a request without a valid signature is ignored even if a header got through. Also in `bench-api.conf` add `proxy_set_header X-BENCH-Client-IP "";` and `proxy_set_header X-BENCH-Client-IP-Signature "";` for every location that serves browsers, so only the web server's own calls (loopback, not through nginx) can set it. If the web server calls the API through the public host name instead of 127.0.0.1:8101, drop that blanking and rely on the signature.

Backend `.env` for this server: `TRUST_PROXY_HEADERS=true`, `TRUSTED_PROXY_IPS=127.0.0.1,::1` (default), `NUM_PROXIES=0`, and `TRUST_CLOUDFLARE_HEADER=false` unless Cloudflare really is in front. After the web change is live remove `THROTTLE_RATES_JSON` from the `.env`.

### 9.3 nginx access log without secrets

Application logs are already masked (`ilaf/logfilters.py`). The nginx access log still prints the e-mail-link paths. Add to `bench-http.conf` (http level) and use the new format instead of `bench` in `bench-web.conf` and `bench-api.conf`:

```nginx
map $request_uri $bench_log_uri {
    default $request_uri;
    ~^(?<head>/(?:join|reset|restore|data-download)/)[^/?]+(?<tail>.*)$        "${head}<token>${tail}";
    ~^(?<head>/api/v1/invites/)(?!lookup|accept)[^/?]+(?<tail>.*)$               "${head}<token>${tail}";
    ~^(?<head>/api/v1/privacy/download/)(?!check)[^/?]+(?<tail>.*)$              "${head}<token>${tail}";
    ~^(?<head>/api/v1/reports/unsubscribe\?token=)[^&]+(?<tail>.*)$             "${head}<hidden>${tail}";
}
log_format bench_masked '$remote_addr - [$time_iso8601] "$request_method $bench_log_uri $server_protocol" $status '
                        '$body_bytes_sent rt=$request_time urt=$upstream_response_time';
```

`$http_referer` is left out on purpose (a token page can show up in it). Keep the 14 day log retention and root/adm-only permissions.

### 9.4 Migration and deploy notes

- Tokens issued before the deploy have no sign-in time, so the first sensitive action after the deploy asks for the password once.
