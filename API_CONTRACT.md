# BENCH API contract (v1)

Standalone product. NOTHING here touches or imports Hope-Backend. The product name is "BENCH" (Business Enhancement Network Cloud Hub, "Your business. One smart identity."), made by the company "iLAF Technologies" (brand and theme follow https://ilaf.qa/, assets in C:\hope\Cardfolio\brand). Names live in one setting / one constant (backend PRODUCT_NAME and COMPANY_NAME, web NEXT_PUBLIC_APP_NAME and COMPANY_NAME).

Brand: the look follows the BENCH site. Font Poppins; colours orange #FF6B35, blue #3B82F6, green #10B981, ink #101114, muted #666B75, line #E8E9ED, soft #F6F7F9. The logo is a text wordmark ("BEN" in ink, "CH" in orange, Poppins 900). The company appears as a quiet "BENCH by [iLAF logo]" lockup (`brand/ilaf-logo.png`, served as `/brand/ilaf-logo.png`) in the landing page, sign-in pages, app sidebar and e-mail footer, and as the text "Powered by BENCH · by iLAF Tech" on public cards (the existing footer switch still turns it off). Backend e-mail colours are the settings `BRAND_ORANGE`, `BRAND_BLACK`, `BRAND_MUTED`, `BRAND_BORDER`, `BRAND_BACKGROUND`; the company short name is `COMPANY_SHORT_NAME`.

Ports in development: backend `http://localhost:8100`, web `http://localhost:3100`.
Base path: `/api/v1/`. JSON in and out. Ids are UUID strings. Times are ISO 8601 UTC.

## Conventions
- Success: HTTP 2xx and the JSON body IS the data (no envelope). Lists are plain arrays unless stated.
- Error: HTTP 4xx/5xx and `{"error": {"code": "<snake_case>", "message": "<plain sentence>", "fields": {"field": ["msg"]}}}` (`fields` only for validation, code `validation_error`).
- Codes used: `validation_error`, `unauthorized`, `forbidden`, `not_found`, `plan_limit` (403), `subscription_required` (402), `invalid_credentials` (401), `email_taken` (409), `slug_taken` (409), `invite_invalid` (410), `throttled` (429). Google, privacy and wallet codes are listed in their sections. The full list of codes is in "Error codes" at the end of this file.
- Auth: `Authorization: Bearer <access>`. Access token 60 min, refresh 30 days, refresh rotates. Public endpoints need no token. Tokens carry `auth_time` (when the person proved who they are); see "Security rules" at the end.
- Limits: every signed-in request is counted per person (reads 600/min, writes 120/min, exports and bulk 12/min, password and sign-in changes 10/min, creating companies, invites and webhooks 60/hour); over the limit answers 429 `throttled` with `Retry-After`. Anonymous endpoints are counted per visitor address.
- Roles in a workspace: `owner`, `admin`, `employee`. Owner and admin manage everything; employee sees and edits only their own card.
- CORS: allow the web origin from env `CORS_ALLOWED_ORIGINS`; public endpoints allow any origin for GET/POST.

## Auth
- `POST auth/register` `{email, password, full_name}` -> 201 `{user, access, refresh}`. Also creates the personal workspace.
- `POST auth/login` `{email, password}` -> `{user, access, refresh}`. A correct password on a disabled account answers 403 `account_suspended` or `account_scheduled_for_deletion`; members of a company that requires Google answer 403 `google_signin_required` (see the sections on Google sign-in and Privacy).
- `POST auth/refresh` `{refresh}` -> `{access, refresh}` (401 `unauthorized` once the refresh token was revoked).
- `POST auth/logout` `{refresh}` (no auth) -> 204, always; that refresh token stops working. `POST auth/logout-all` (auth) -> `{revoked: n}`; every refresh token of the person is revoked (access tokens already issued live until they expire, at most 60 minutes).
- `GET auth/me` / `PATCH auth/me` `{full_name?, language?}` -> user `{id, email, full_name, photo_url, created_at, email_verified, has_password, google_linked, google_email, language}`
- `POST auth/forgot` `{email}` -> 204 (always). `POST auth/reset` `{token, password}` -> 204. `POST auth/change-password` `{old_password, new_password}` -> 200 `{access, refresh}`: every other session is signed out (refresh tokens revoked), the answer holds fresh tokens for the current device. A password reset signs out every session too, and only the newest reset link works. Unknown address, wrong password and a Google-only account all take the same time and give the same 401 on login.
- `GET me/workspaces` -> `[{id, kind: "personal"|"company", name, role, card_count, subscription: Subscription}]`

## Plans and billing
Plan: `{code, name, kind: "personal"|"company", interval: "year"|"month", price_minor, currency, max_cards, per_seat: bool, min_seats, features: [string]}`
- `GET plans` (public) -> `[Plan]`. Seed (placeholder prices, editable in admin): `personal` (1 card, QAR 4900/year), `business` (5 cards, QAR 9900/year), `company` (per seat, min 5 seats, QAR 3900/seat/year, one card per seat).
- `POST workspaces/{id}/checkout` `{plan_code, seats?}` -> `{checkout_url}`. Stripe Checkout, one-time payment for the period (own engine, no Stripe Billing). If `STRIPE_SECRET_KEY` is empty and `DEBUG`, or `CARDS_DEV_ACTIVATE=true`, the plan activates at once and `checkout_url` is `<WEB_BASE_URL>/app/billing?paid=1`.
- `POST stripe/webhook` (no auth, Stripe signature) -> 200. `checkout.session.completed` activates or extends the subscription. Idempotent on session id.
- `GET workspaces/{id}/subscription` -> Subscription `{status: "none"|"active"|"expired", plan_code|null, seats_total, seats_used, starts_at|null, ends_at|null, grace_ends_at|null, live: bool}`. `live` = active and now <= ends_at + `CARDS_GRACE_DAYS` (7).
- `GET workspaces/{id}/invoices` -> `[{id, number, amount_minor, currency, plan_code, paid_at}]`
- Renewal: before expiry a reminder email; paying again extends from `ends_at` if still within grace, else from now. (Automatic renewal is NOT built.)

## Workspaces
Brand: `{company_name, logo_url|null, website, design: Design, lock_design: bool, show_footer: bool}` plus the company branding keys and picture URLs listed under "Company branding" below.
- `POST workspaces` `{name, country?}` -> 201 company workspace, caller is owner, no subscription yet. `country` is an ISO 3166-1 alpha-2 code from the built-in list (`backend/ilaf/countries.py`, the same codes as `web/src/lib/countries.ts`); lower case is accepted and stored upper case; `""` or `null` means none; a code that is not in the list -> 400 `validation_error` on `country`. The workspace JSON carries `country` (`null` for companies that never chose one, and for personal workspaces). `PATCH workspaces/{id}` takes `{country}` too (owner and admin, company workspaces only; a personal workspace -> 400); a change is logged in the activity log as `brand.updated` with key `country`. Staff: `GET staff/companies` rows carry `country` (the company's own code or `""`), `GET staff/companies/{id}` carries `country` (own code, else the visitor-based guess) and `country_guessed` (true for the guess), and `GET staff/analytics` has `company_countries: [{country, companies, guessed}]` (companies per country, the own country first; `guessed` is how many of them are counted by the visitor guess) next to the visitor views `countries`. An announcement aimed at a country uses the same rule.
- `GET workspaces/{id}` -> `{id, kind, name, role, brand, custom_domain|null, subscription}`
- `PATCH workspaces/{id}` `{name?, brand?: partial, custom_domain?}` (owner/admin)
- `POST workspaces/{id}/logo` multipart `file` -> `{logo_url}`; `DELETE workspaces/{id}/logo` -> 204 (owner/admin, also on personal workspaces)
- When `lock_design` is true every card in the company renders with `brand.design` and employees cannot change design fields (ignored on write, never an error).

## Company branding
Company workspaces (kind `company`) store a palette, logo display options and card artwork in `Workspace.brand`. Every card of the company renders with them. All keys are optional; old brands get the defaults when read.

Brand keys added to `Brand` (read from `GET workspaces/{id}`, written with `PATCH workspaces/{id}` `{brand: {...}}`, partial updates merge; `artwork` merges one level deeper, so `{artwork: {pattern: {size: "s"}}}` changes only that value):
```
colours: null | {primary: "#rrggbb", accent: "#rrggbb", mode: "brand"|"light"|"dark"}
palette: null | {bg, bg2, fg, acc, on}            // all "#rrggbb"
logo_display: "auto"|"symbol"|"symbol_name"|"full"          // default "auto"
logo_placement: "card"|"above"|"both"                       // default "both"
logo_corner: "auto"|"tl"|"tr"|"bl"|"br"                     // default "auto"
logo_chip: "auto"|"always"|"never"|"white"|"black"          // default "auto"
show_company_name: bool                                      // default true (the name beside a symbol)
artwork: {
  mode: "none"|"background"|"pattern"|"template",            // default "none"
  background: {kind: "sample"|"upload"|"none", sample: string|null, strength: 0..100},   // defaults none, null, 60
  pattern: {enabled: bool, size: "s"|"m"|"l", spacing: "tight"|"normal"|"wide", angle: 0|-15|-30, opacity: 5..60, combine_with_background: bool},  // defaults false, m, normal, 0, 18, false
  template: {kind: "sample"|"upload"|"none", sample: string|null, zone: "A"|"B"|"C"|"D", text_colour: "auto"|"#rrggbb", text_size: "s"|"m"|"l"}  // defaults none, null, A, auto, m
}
```
plus read-only URLs in the same object: `logo_url`, `symbol_url`, `background_url`, `template_front_url`, `template_back_url` (each `string|null`).
- The client computes `palette` from `colours` (same algorithm as the design preview) and sends both. The server validates: valid hex, `fg` on `bg` contrast >= 4.5, `fg` on `bg2` >= 4.5, `on` on `acc` >= 3.0 (WCAG). Otherwise 400 `validation_error` with `fields["brand.palette"]` naming the unreadable pair in plain words. `palette: null` removes company colours: the company design's colour 4 becomes 0 and cards holding colour 4 render as 0.
- Sample ids. `background.sample`: `geo`, `mesh`, `photo`, `stripes`, `dots`, `topo`. `template.sample`: `harbor`, `terra`, `night`. A sample id is required when `kind` is `sample` (otherwise it is stored as null). `kind: "upload"` needs the matching picture uploaded first (`background` for the background, `template-front` for the template), else 400 on `brand.artwork.background.kind` / `brand.artwork.template.kind`. Deleting that picture sets its `kind` back to `none`.
- Errors use the usual shape with dotted keys, for example `{error: {code: "validation_error", fields: {"brand.palette": [...], "brand.artwork.pattern.opacity": [...]}}}`. Unknown keys are refused. `brand.design.colour` is refused with colour 4 when the company has no palette (checked after the palette in the same request is applied, so `{palette, design: {colour: 4}}` works in one call).
- Locked design: when `lock_design` is true, `colour` (including 4) comes from the company design like the other locked keys.
- Personal workspaces: the new keys are read as defaults (`palette: null`, ...) and URLs are null. Explicit writes of any new key, and uploads or deletes of the four new pictures, return 400 `validation_error`. Brand PATCHes that do not mention the new keys still work.

Picture files (owner/admin only, same permission rules as the logo: member of another workspace 404, employee 403, no token 401; company workspaces only, else 400):
- `POST workspaces/{id}/symbol` multipart `file` -> `{symbol_url}`: PNG, JPG or WebP (max 3 MB), fitted inside 1024 px, stored as PNG keeping transparency.
- `POST workspaces/{id}/background` -> `{background_url}`: PNG, JPG or WebP (max 3 MB), long side max 1600 px, stored as JPEG.
- `POST workspaces/{id}/template-front` -> `{template_front_url}` and `POST workspaces/{id}/template-back` -> `{template_back_url}`: same as the background.
- `DELETE` on the same four paths removes the file -> 204 (also when there is none).
- SVG is refused everywhere (400, message says to use PNG, JPG or WebP), like GIF and files that are not images. Files get random 32-character names under `media/brand/`; a replaced file is deleted.

Public payload: for a company card `card.brand` is `{company_name, logo_url, symbol_url, palette, logo_display, logo_placement, logo_corner, logo_chip, show_company_name, artwork, background_url, template_front_url, template_back_url}` (`palette` is null when the company has none); for a personal card it is `null`. `card.design` is the effective design (locked company design applied, colour 4 turned into 0 when there is no palette).

## Cards
Design (v3, the numbered design library; replaces the named-face and free-colour design): `{face, colour, below, intro, font, size, photo, brand_colors, foot}`
- `face`: whole number 1 to 500, the card face on top of the page. Faces 1 to 25 are the original 25 in the old order (classic, split, monogram, edge, portrait, frame, swiss, bubble, bands, glass, neon, terminal, ticket, magazine, arch, wave, corner, stack, blueprint, pills, orbit, letterpress, aurora, dotmatrix, ribbon). Every face flips to a QR back.
- Faces 401 to 500 are Design Pack 2 (`web/scripts/pack2`, built by `npm run build:pack2`). They sit behind the feature switch `pack2_faces` (on by default, like every switch): while it is off for the card's company, a design write that picks a face above 400 (`PATCH cards/{id}`, the company brand design, a department design) answers 403 `feature_unavailable`, and the web design picker hides those faces; cards that already hold such a face keep rendering it. A face above 500 is a plain 400 `validation_error`, as before.
- `colour`: whole number 0 to 4. 0 to 3 pick one of the face's own four colourways; 4 means company colours (the company palette, see "Company branding"). 4 is only accepted when the card's workspace is a company that has a palette, otherwise 400 `validation_error` on `design.colour`. A card holding 4 whose company has no palette (any more) renders as 0 (the effective design), without an error. The colours themselves (background, second background, text, accent, text on accent) come from the design library, so the card, its icons and the area below always match. There are no free colours.
- `below`: whole number 1 to 400, how the area below the card is laid out. Layouts 1 to 12 are the original 12 in the old order (list, grid, spec, chips, brand, contacts, timeline, bento, dock, editorial, tabs, accordion).
- `intro`: whole number 0 to 400, the opening animation played once when a visitor opens the card. 0 is no animation, 1 is fade-up (default). 1 to 22 are the original 22 in the old order (fade-up, fade-in, zoom, elastic, drop, blur, slide-left, slide-right, flip, cube, unfold, book, spin, deal, envelope, curtain, door, shutter, spotlight, wipe, typewriter, ripple).
- `font`: string, `"face"` (default) keeps the fonts each face was drawn with; otherwise one of `poppins`, `outfit`, `manrope`, `space-grotesk`, `playfair`, `cormorant`, `lora`, `oswald`, `bebas`, `jetbrains`, `caveat`, `dancing` (Latin) or `plex-arabic`, `cairo`, `tajawal` (made for Arabic). It sets the typeface of the name, title, role/company and contact lines of the card face; Arabic text on the card gets the Arabic font matched to the chosen one automatically. A face that draws its own lettering on purpose (terminal, 8-bit, typewriter and similar, about 20 faces) ignores it; the web app lists them in `FONT_LOCKED_FACES` and tells the owner. Any other value, or a non-string, is `validation_error` on `design.font`.
- `size`: whole number 60 to 150 (default 100), the size of the name, title and contact lines together, in percent of what the face draws. Floats, strings and booleans are refused (`design.size`). The number is the size the owner asked for: the page shows it only where it fits. The browser measures the face and holds an enlarged size to the largest one that adds no overlap or clipping (never below 100% for a request above 100%); the server's first HTML applies `min(size, 100)%` so a page without scripts never overlaps.
- `photo`: bool, true shows the card photo on faces that have a photo slot, false shows initials. `brand_colors`: bool as before. `foot`: bool, shows "Powered by BENCH".
- The library (faces, layouts, openings, colourways, in number order) lives in the web app's design library module, built from `C:\hope\Cardfolio\design-reference\ilaf_one_card_designs.html`.
- Locked by a company design lock: face, colour (including 4), below, intro, font, size (the card keeps its own `photo`, `brand_colors` and `foot`). Out-of-range or non-whole numbers, and every old key (layout, bgm, btn, shape, cover, addr, acts, bg, bg2, fg, acc, on, details), are rejected with `validation_error`. A card or company design stored before `font` and `size` existed reads as `font: "face"`, `size: 100`; no migration is needed (the design is JSON).
- A data migration converts existing cards and company brand designs: a named face, details style or intro maps to its position in the old order (so the same number); colours become colourway 0; intro none becomes 0. The previous design is kept in `legacy_design` / `legacy_brand_design`.
Card also has `cover_url: string|null` (a wide picture used by the glass, bands and magazine faces) and `POST cards/{id}/cover` multipart `file` (JPG, PNG or WebP, max 3 MB, rejected if SVG) -> `{cover_url}`, resized to 1280x800 JPEG. The company brand `design` uses this same schema. Public payload `card` carries `design` (effective), `cover_url`, `photo_url`.
VcardOptions: `{company, photo, phones, emails, urls, social, addr: bool, note: string}`
Icon: `{type: "auto"|"brand"|"lucide"|"upload", key: string|null, image_url: string|null}`. `null` or `auto` = pick the logo from the kind or from the link's domain. `brand` = a brand logo by Simple Icons slug in `key` (about 3,000 brands: any app, mail service, social network, shop). `lucide` = a generic icon by Lucide name in `key`. `upload` = the owner's own image in `image_url`. Any item kind may carry an icon override.
Any link is allowed: the `Custom` kind takes any URL, email address or phone number plus a `label` and an `icon`; the value is normalised (an email becomes `mailto:`, a phone number becomes `tel:`, a bare domain gets `https://`). Max 40 items per card, label max 40 chars.
Allowed link schemes (one list, in one place in the code, easy to extend): http, https, tel, mailto, sms, skype, tg, viber, facetime, facetime-audio, geo. Everything else (javascript, data, vbscript, file, blob) is rejected with `validation_error`.
Item kinds: Mobile, Landline, WhatsApp, Email, SMS, Location, Website, Facebook, Instagram, LinkedIn, X, YouTube, TikTok, Snapchat, Telegram, Pinterest, Threads, GitHub, Behance, Dribbble, Discord, Spotify, SoundCloud, Twitch, Reddit, Medium, Calendly, AppStore, GooglePlay, PayPal, Meeting, Custom (Meeting is described under "Card features").
Card: `{id, workspace_id, owner: {id, full_name, email}|null, public_code, public_url, slug|null, status: "draft"|"published"|"suspended", name, title, company, address, photo_url|null, save_contact: bool, vc: VcardOptions, features: Features, design: Design, items: [{id, kind, value, label, on, order, icon: Icon|null}], created_at, updated_at, stats: {views, scans, saves, leads}}`
- `GET workspaces/{id}/cards` (employee: own only) / `POST workspaces/{id}/cards` -> 201. Over the limit -> 403 `plan_limit`. No live subscription -> 402 `subscription_required`.
- `GET|PATCH|DELETE cards/{id}`. PATCH takes any card field; `items` is a full replacement list (order = array order). `public_code` never changes. Changing `slug` keeps old slugs working (slug history).
- `POST cards/{id}/photo` multipart `file` -> `{photo_url}` (resized to max 800 px, JPEG)
- `POST cards/{id}/icon` multipart `file` (PNG, JPG or WebP, max 1 MB; SVG is rejected for safety) -> `{image_url}`, resized to a 128 px square PNG. Use the URL as `icon: {type: "upload", image_url}` on an item.
- `POST tools/resolve-link` (auth) `{url}` -> `{url, title|null, favicon_url|null}`: normalises the link, reads the page title, and, when the site is not a known brand, fetches its favicon once and stores it so visitors never call third parties. The fetch must be SSRF-safe: http/https only, resolve the host first and refuse private, loopback and link-local addresses (also after every redirect), 3 s timeout, 1 MB cap, no cookies, max 3 redirects. On any failure return nulls, never an error.
- `POST cards/{id}/publish`, `POST cards/{id}/unpublish`, `POST cards/{id}/duplicate`
- `GET slugs/check?slug=` -> `{available: bool, suggestion|null}`
- `public_code`: 10 chars from `abcdefghjkmnpqrstuvwxyz23456789`, random, permanent. `public_url` = `<WEB_BASE_URL>/c/<slug or public_code>`.

- `GET workspaces/{id}/members`

## Leads
Lead: `{id, card_id, card_name, name, email, phone, company, note, source, channel, meeting_times: [string], status: "new"|"contacted"|"qualified"|"won"|"lost", assignee, assigned_at, consented_at, note_count, created_at}` (assignment, notes and the timeline are in "Leads, analytics and reports"). `source` says where the lead came from: `exchange` (a visitor used Share your details), `meeting_request` (a visitor used the built-in meeting form), `scanned_card` (the user scanned a paper card), `event` (a member noted someone met in person, see Event mode below), or one of the older `link`, `qr`, `nfc`, `email`. Lead also carries `tag` (`hot`, `warm`, `follow_up` or empty) and `event_name` (text, for event leads). `channel` is how the visitor reached the card (`nfc`, `qr`, `link`, `email`, or empty).
- `GET workspaces/{id}/leads?card_id=&q=&status=&limit=50&offset=0` -> `{count, results: [Lead]}` (employee: own cards only)
- `POST workspaces/{id}/leads` `{name, email?, phone?, company?, note?, card_id?, source?: "scanned_card"|"event", tag?: "hot"|"warm"|"follow_up", event_name?, client_ref?}` -> 201 Lead with `source: "scanned_card"` (default) or `"event"`. For `source: "event"` the name is optional as long as name, email, phone, company or note says who the person is (400 on `name` otherwise). `client_ref` (up to 64 characters, made up by the phone) makes a retry safe: a second request with the same `client_ref` from a member who can see that lead answers 200 with the lead already saved instead of adding a duplicate. Any other `source` or `tag` -> 400 on that field. Event mode in the web app queues notes made offline and sends them with this call when the connection returns.
  (any member; no e-mail is sent; an employee's lead is attached to their own card, a manager's to the chosen card or to the company; `card_id` must be one of the caller's visible cards, else 400).
- `PATCH leads/{id}` `{status?, assignee_id?}`; `GET workspaces/{id}/leads.csv` -> text/csv (see "Leads, analytics and reports")

## Analytics
`GET workspaces/{id}/analytics?days=30&card_id=` ->
`{totals: {views, unique_visitors, scans, taps, saves, leads, link_clicks}, prev_totals: same, series: [{date, views, saves, leads}], sources: [{key: "nfc"|"qr"|"link"|"email"|"other", count}], locations: [{country, count}], devices: [{key: "ios"|"android"|"desktop"|"other", count}], hours: [24 ints, UTC], top_buttons: [{kind, count}], cards: [{card_id, name, views, saves, leads}]}`

## Public (no auth, throttled, CORS open)
- `GET public/cards/<code_or_slug>` -> one of
  - `{state: "live", canonical: "<slug or code>", card: {name, title, company, address, photo_url, items: [{kind, value, label}] (only on and non-empty, in order), save_contact, features: PublicFeatures, design (effective, brand design when locked), footer: bool, brand: {company_name, logo_url, symbol_url, palette, logo_display, logo_placement, logo_corner, logo_chip, show_company_name, artwork, background_url, template_front_url, template_back_url}|null (company cards only, see Company branding), public_url, vcard_url, qr_url}, og: {title, description, image_url|null}}`
  - `{state: "paused", company_name|null, message}` when the subscription is not live
  - `{state: "suspended", company_name|null, website|null, message}` for a removed employee or admin-suspended card
  - 404 `not_found` only for an unknown code
- `POST public/cards/<code>/events` `{type: "view"|"tap"|"save"|"link_click", source?: "nfc"|"qr"|"link"|"email", kind?}` -> 204
- `POST public/cards/<code>/leads` the exchange-contact form, see "Card features". -> 201 `{ok, vcard_url}`.
- `POST public/cards/<code>/meeting-requests` the built-in meeting request, see "Card features". -> 201 `{ok}`.
- `GET public/cards/<code>/vcard` -> `text/vcard; charset=utf-8` attachment, vCard 3.0, honours `vc` options, social links as `itemN.URL` + `itemN.X-ABLabel`, WhatsApp as TEL (not duplicated), photo base64 256 px when `vc.photo`.
- `GET public/cards/<code>/qr.svg?size=512` -> SVG of `public_url?s=qr`. NFC tags should use `?s=nfc`.
- Share preview image: the web app (not the API) serves `GET /c/<code>/og.png` (1200 x 630 PNG drawn on the server from the public card: name, title, company, photo, company logo and the card's colours, with a product footer; a missing, paused or removed card gets a plain product picture; `Cache-Control: public, max-age=3600, stale-while-revalidate=86400`). The card page's Open Graph and Twitter tags point at it.
- `GET public/cards/<code>/qr.png?size=512` -> the same code as a PNG (128 to 1024 px, default 512), `Cache-Control: public, max-age=86400`. For e-mail signatures and documents, where an SVG does not load.

## Admin and jobs

## Security rules
- Client address: forwarded headers count only when the TCP peer is in `TRUSTED_PROXY_IPS` (default loopback) and `TRUST_PROXY_HEADERS` is on. Order: `X-BENCH-Client-IP` (sent by the web server; with `CLIENT_IP_HEADER_SECRET` set it needs `X-BENCH-Client-IP-Signature` = hex HMAC-SHA256 of the address), `CF-Connecting-IP` (only with `TRUST_CLOUDFLARE_HEADER=true`), then `X-Forwarded-For` read from the right. Invalid values are ignored; IPv6 visitors share one counter per /64.
- Re-authentication: `POST auth/google/link` `{credential, password?}`, `auth/google/unlink`, `auth/set-password` (`credential?` for Google-only accounts), `privacy/export` and `privacy/requests/{id}/download-link` need a sign-in within `REAUTH_WINDOW_SECONDS` (600) or `password` / `credential` in the body; otherwise 403 `reauth_required` with `fields.password`. A wrong password is 400. Linking Google when another Google account is already linked is 409 `google_already_linked`.
- Revocation: refresh tokens are revoked on reset and change of password, `auth/logout`, `auth/logout-all`, a requested account deletion, and when a member is removed, suspended or demoted from admin (they sign in again).
- Company rules for employees: new rule keys `slug`, `features`, `vcard` in `field-rules` (`free` or `locked`; `approval` behaves as `locked`); `field_access` on a card carries them. An employee creating a card gets the seat's name and title when those are locked or under approval, only the mandatory buttons when adding buttons is not free, and nothing for locked settings. Admins cannot publish, unpublish, suspend, restore, delete or reassign the card of the owner or of another admin (403); the owner can do all of it.
- Uploads: only real JPEG, PNG or WebP (decided by the first bytes, not the name), still pictures, at most 40 megapixels (`IMAGE_MAX_PIXELS`) and 12000 px a side; everything else, GIF and ICO included, is 400. Website favicons may also be `.ico`.
- Public events: `kind` is stored only when it is a real button kind. Public lead form: at most `LEAD_MAX_PER_CARD_PER_DAY` (300) saved forms per card per day (429), at most `LEAD_NOTIFY_MAX_PER_RECIPIENT_PER_DAY` (100) lead e-mails per address per day (the lead is still saved); an e-mail subject never carries a link or address from the visitor's name.
- Date filters: years outside 1970 to 2100 are 400. A badly formed id is 404.
- Retention: `manage.py prune_analytics` (daily). Visit events older than `ANALYTICS_RETENTION_DAYS` (400) are rolled into 15-minute summary rows (`weight` = how many events; no visitor hash), so every total and chart stays the same except unique visitors for days older than that; finished webhook deliveries older than 90 days, reset rows older than a day and links of invitations expired a week ago are deleted; audit entries are kept.
- Logs: token paths and query tokens are masked in the application log (`ilaf/logfilters.py`).

## Company operations
Company workspaces only (owner and admin unless noted). Personal workspaces answer 400 on these routes. Every admin action below writes an audit event.

Member gains `title`, `department_id`, `department_name`, `invite_sent_at`, `can_resend_at` (only while invited). Card gains `seo_indexable` (boolean, default false; `PATCH cards/{id}` accepts it; the public payload `card.seo_indexable` tells the web page whether to send `noindex`), `hide_from_directory`, `field_access`, `pending_changes: [{id, field, created_at}]`, `submitted_for_approval: [field]` (fields of the last write that were sent for approval instead of saved). Brand gains `lock_allows_departments`, `directory_enabled`, `directory_slug`. Lead `card_id` may be null (card deleted); `card_name` stays.

Resend invite: `POST workspaces/{id}/members/{mid}/resend-invite` -> Member. Only for `invited` members. New token (the old link stops working) and a new 30-day expiry. One send per 10 minutes per member, counting the first invite email: otherwise 429 `throttled` with `Retry-After`.

Reassign: `POST cards/{id}/reassign` `{member_id: uuid|null, reset_details?: bool}` -> Card. `null` = unassigned (shared company card). `public_code`, slug, QR and link never change. The new holder must have no other card (409 `target_has_card`). A suspended card returns to its previous status when the holder is active; a suspended holder keeps it suspended. `reset_details` copies the holder's name and title onto the card.

Offboarding: `DELETE workspaces/{id}/members/{mid}` body `{card: "keep"|"reassign"|"delete", reassign_to?: member_id|null}`. `keep` (default) suspends the card and detaches it; `reassign` as above (null = nobody); `delete` deletes the card. Leads always stay with the company (shown with `card_id: null`). Also `POST cards/{id}/suspend` and `POST cards/{id}/restore`.

Bulk: `POST workspaces/{id}/bulk/members` `{action: publish|unpublish|suspend|restore|role|department|remove, ids: [..<=200], role?, department_id?, card?, reassign_to?}` and `POST workspaces/{id}/bulk/cards` `{action: publish|unpublish|suspend|restore|delete, ids}` -> 200 `{action, total, ok, failed, results: [{id, name, ok, reason|null, code|null}]}`. Items are independent; refused items carry a plain reason. `role` is owner only (403 for the whole request). More than 200 ids, an empty list or an unknown action is a 400. Writes one audit event per item plus one `bulk.run` summary (items share `details.bulk_id`).

Audit: `GET workspaces/{id}/audit?actor=<user id>&action=<key or "group.">&from=YYYY-MM-DD&to=YYYY-MM-DD&q=&page=&page_size=` -> `{count, page, pages, page_size, results: [{id, action, label, actor: {id, full_name, email}|null, target_type, target_id, target_label, details, created_at}], actors, actions}`; `GET workspaces/{id}/audit.csv` takes the same filters. Rows are append-only (no update or delete route; the model refuses both). Actions: invite.sent, invite.resent, member.role_changed, member.removed, member.suspended, member.restored, member.department_changed, card.published, card.unpublished, card.suspended, card.restored, card.deleted, card.reassigned, brand.updated, brand.design_changed, brand.lock_changed, brand.logo_changed, department.created, department.updated, department.deleted, fields.rules_changed, change.requested, change.approved, change.rejected, directory.updated, bulk.run. Only a one-way hash of the caller address is stored.

Departments: `GET|POST workspaces/{id}/departments`, `GET|PATCH|DELETE workspaces/{id}/departments/{did}`, `POST workspaces/{id}/departments/{did}/assign` `{member_ids}` (bulk result). Department `{id, name, design: {face?, colour?, below?, intro?, font?, size?}, items: [{kind, value, label}], mandatory_items, member_count}`. Names are unique per company without case. Invites (`department_id` per entry), `PATCH members/{mid}` `{department_id}` and the CSV import (`department` column, existing names only) set a member's department. A new invite starts its draft card from: company design, department design keys, company website button, department `items`, then every mandatory button. Existing cards are not rewritten. Design rule: with the lock off the card keeps its own design (started from the department); with the lock on the company design applies everywhere, except that when `brand.lock_allows_departments` is true the department's design keys win for its people. A department manager role is NOT built.

Field rules: `GET|PATCH workspaces/{id}/field-rules`. `{name, title, photo, company, address, button_add, button_edit, button_remove: "free"|"approval"|"locked", allowed_kinds: [kind]|null, banned_domains: [domain], mandatory_buttons: [{kind, value, label}]}`. Owners and admins bypass all of it. For employees: a changed locked field is 403 `field_locked` (with `fields`); an approval field is left unchanged and recorded as a change request; a button list that adds, edits or removes visible buttons needs the matching permission (any `approval` sends the whole new list for approval, any `locked` refuses); kinds outside `allowed_kinds` and links to a banned domain (subdomains and email domains included) are 400 `validation_error`; a mandatory button (company list plus the member's department list) cannot be removed, switched off or changed (403), and is added back when a write does not contain it. A photo upload follows `photo`: locked 403, approval answers `{photo_url: <current>, pending: true, change_id}`.

Change requests: `GET workspaces/{id}/change-requests?status=pending|approved|rejected|withdrawn|superseded|all&card_id=` -> `{count, pending_count, results: [{id, card_id, card_name, field, old, new, status, requested_by, decided_by, decided_at, reason, created_at}]}` (`field` is name, title, company, address, photo or buttons; a photo is `{url}`; buttons are item lists). `POST workspaces/{id}/change-requests/{cid}/approve|reject` `{reason?}`, `POST workspaces/{id}/change-requests/bulk` `{action: approve|reject, ids, reason?}` (bulk result), `POST change-requests/{cid}/withdraw` (the employee who asked). A new request for the same field replaces the waiting one. Deciding twice is 409 `not_pending`. Admins get an email when a request arrives, the employee when it is decided.

Directory: brand keys `directory_enabled` (default false) and `directory_slug` (unique, same shape as a card slug, reserved words refused; 409 `slug_taken`), written through `PATCH workspaces/{id}` by the owner only. `GET public/directory/<slug>?q=&department=<id>&page=&page_size=` (no auth, throttled `public_directory`, default 60/min) -> `{company: {name, slug, website, logo_url, symbol_url, palette, logo_display, show_company_name}, total, count, page, pages, page_size, departments: [{id, name, count}], results: [{code, name, title, department, photo_url, url}]}` or 404 when the directory is off or unknown. Listed: published cards of active members, company plan live, not `hide_from_directory`. Never listed: drafts, suspended cards, unassigned cards. No email or phone. Web page: `/d/<slug>`.


## Card features
Per-card switches and the two visitor forms. Added by migrations `cards.0006`, `workspaces.0007` and `leads.0004` (run `migrate`).

Features: `{exchange: {enabled: bool, fields: {email, phone, company, note: "off"|"optional"|"required"}, consent_text: string}}`. Defaults: enabled, every field optional, empty consent text (the public page then says "I agree that <name> may store my details and contact me."). The name is always asked. Email and phone cannot both be `off` (400 `validation_error`, key `features.exchange.fields`). Written with `PATCH cards/{id}` `{features: {...}}`; a partial object is merged onto the stored one; unknown keys are ignored; bad values are 400 with dotted keys (`features.exchange.enabled`, `features.exchange.fields.email`, `features.exchange.consent_text` max 300).

PublicFeatures (in the public card payload): `{exchange: {enabled, fields, consent_text (the sentence to show, default filled in), privacy_url: string|null}, meeting_form: bool}`. `meeting_form` is true when the card has a switched-on Meeting button set to the built-in form. The card owner's e-mail address is never part of it.

Lead settings of the workspace (stored on `Workspace.lead_settings`): `{privacy_url: string, notify_admins: bool}`. `GET workspaces/{id}/lead-settings` (any member), `PATCH workspaces/{id}/lead-settings` (owner and admin, else 403). `privacy_url` is an http(s) address (a bare domain gets https://; empty clears it); the consent line on the public forms links to it. `notify_admins` (company workspaces) adds every active owner and admin to the e-mail about each new lead; the card holder is always told (a card with no holder tells the admins).

Exchange contact: `POST public/cards/<code>/leads` (no auth, throttle `public_lead`) body `{name, email?, phone?, company?, note?, consent: true, opened_at, source?: "nfc"|"qr"|"link"|"email", website_url}`. Fields set to `off` are ignored, `required` ones must be present, and when email and phone are both optional one of them is needed. `consent` must be true (400 `validation_error` on `consent`). On success: a Lead with `source: "exchange"`, `channel` from `source`, `consented_at` set, an e-mail to the card holder (and admins when asked), and `201 {ok: true, vcard_url}` where `vcard_url` is the card owner's contact file (the "Send me yours" download). The switch off answers 403 `feature_off`. Draft and suspended cards answer 404.
Spam checks, in order: honeypot `website_url` filled -> 201 and nothing saved; `opened_at` (milliseconds since 1970, set when the form was opened) must be 3 to 86400 seconds old, else 400 `too_fast` (setting `LEAD_MIN_FILL_SECONDS`, default 3); more than `LEAD_MAX_PER_CARD_PER_HOUR` (default 5) saved forms from one address for one card in an hour -> 429 `throttled`; then the usual per-address throttle. Only saved forms count toward the hourly cap.

Meeting button: item kind `Meeting`. Its value is either an https booking link (Calendly, Google Calendar appointment page, Cal.com, Microsoft Bookings or any https address; a bare domain gets https://; http, other schemes, spaces, no dot in the host and addresses with a user name are 400 `validation_error` on the item's `value`) or the word `form` (any case, stored as `form`) for the built-in request form. The public item `href` is the link, or `#meeting-request` for the form. Known providers (calendly.com, calendar.app.google, calendar.google.com, cal.com, outlook.office365.com, outlook.office.com, bookings.microsoft.com, book.ms, tidycal.com, savvycal.com, meetings.hubspot.com, zoom.us) are recognised by host suffix; the web app shows their logo and colour and the label "Book on <name>". Meeting links are written to the contact file as labelled web links.

Meeting request: `POST public/cards/<code>/meeting-requests` body `{name, email, times: [string] (1 to 3, each up to 80 characters, free text), message?, phone?, consent: true, opened_at, source?, website_url}`. Needs a switched-on Meeting button set to `form` on the card, else 403 `feature_off`. Same honeypot, `too_fast` and hourly cap as above. Creates a Lead with `source: "meeting_request"`, `note` = the message, `meeting_times` = the times, and e-mails the card holder (and admins when asked) -> `201 {ok: true}`.

Scanned paper card: `POST workspaces/{id}/leads` (see Leads) with `source: "scanned_card"`. The photo is read in the browser; only the reviewed fields reach the API.

Media pictures (`/media/`) are served with `Access-Control-Allow-Origin: *`, so the call-background maker can draw a company logo on a canvas and still save the image. With an S3-compatible bucket, give the bucket the same CORS rule.

## Sign in with Google
The browser gets a signed Google ID token ("credential") from Google Identity Services and sends it here. No client secret is used. The token is checked (RS256 signature against Google's public keys, issuer, audience = `GOOGLE_CLIENT_ID`, expiry) and `email_verified` must be true. Without `GOOGLE_CLIENT_ID` every Google route answers 503 `google_not_configured` and the web app hides its button.

User gains `email_verified`, `has_password`, `google_linked`, `google_email` (read in `GET auth/me`, login and register answers). `email_verified` becomes true after a Google sign-in, a password reset or an invite accepted through the e-mailed link; a plain password sign-up is not verified.

- `POST auth/google` `{credential}` -> `{user, access, refresh}` (201 when the account was just created, else 200). Rate limit scope `auth_google` (20/min per address). Rules, in order: the Google id (`sub`) wins; else an account with the same address is linked only when its `email_verified` is true (otherwise 409 `account_exists_unverified`: the person signs in with the password and connects Google in settings, which stops anyone pre-registering a victim's address); a different Google id already linked to that account is 409 `google_account_mismatch`; else a new account without a password is created with a personal workspace, exactly like `auth/register`. Suspended accounts get 403 `account_suspended`; accounts waiting for deletion get 403 `account_scheduled_for_deletion` (see Privacy).
- `POST auth/google/link` `{credential}` (auth) -> user. 409 `google_in_use` when that Google account belongs to someone else.
- `POST auth/google/unlink` (auth) -> user. 409 `no_other_sign_in` unless the account has a password; 403 `google_signin_required` when a company requires Google for this person.
- `POST auth/set-password` `{new_password}` (auth) -> 204, only for accounts without a password (else 409 `password_exists`; those use `auth/change-password`).
- `POST invites/<token>/accept-google` `{credential}` -> `{access, refresh, workspace_id}`. The Google address must equal the invited address (403 `invite_email_mismatch`) and be inside the company's allowed domains (403 `domain_not_allowed`); creates or links the account and activates the seat.
- Login with a password answers 403 `google_signin_required` for people who hold a non-owner seat in a company with `require_google_signin`. `POST invites/<token>/accept` (password) answers the same for such a company, and 403 `domain_not_allowed` for an address outside the allowed domains.

Company sign-in rules (company workspaces, read by owner and admin, written by the owner only): `GET workspaces/{id}` carries `security: {allowed_email_domains: [domain], require_google_signin: bool}` (null for others and for personal workspaces); `PATCH workspaces/{id}` `{security: {allowed_email_domains?, require_google_signin?}}` (max 20 domains, lower-cased, a leading `@` is removed; invalid domain -> 400). Invites to other domains are refused at creation (`invites.N.email`) and at acceptance; the CSV import skips them with a reason. Audit action `company.security_changed`.

Owner setup (Google Cloud Console, about ten minutes):
1. console.cloud.google.com: create a project (or pick one). APIs and Services, OAuth consent screen: user type External, app name = the product name, support e-mail, authorised domain = the web domain. Scopes: only `openid`, `email`, `profile` (no verification review needed). Publish the app ("In production") so everyone can sign in, not only test users.
2. APIs and Services, Credentials, Create credentials, OAuth client ID, application type Web application. Authorised JavaScript origins: `https://<web domain>` (and `http://localhost:3100` for development). Authorised redirect URIs: leave empty (the one-tap/popup button needs none). No client secret is needed or stored.
3. Copy the Client ID (`123-abc.apps.googleusercontent.com`) into the backend environment as `GOOGLE_CLIENT_ID` and into the web build as `NEXT_PUBLIC_GOOGLE_CLIENT_ID` (a build-time value, so rebuild the web app after setting it).

## Privacy and data (export and delete)
Every export or deletion is one `DataRequest` row `{id, kind: "export"|"delete", scope: "user"|"workspace", user, workspace, status: pending|processing|ready|completed|cancelled|expired|failed, requested_at, due_at (requested + 30 days), completed_at, handled_by (staff user), scheduled_for (deletion date), file_name, file_size, ready_at, expires_at, downloaded_at, details, error}`; the future admin dashboard reads this table (registered in the Django admin already). JSON shape: `{id, kind, scope, workspace_id, workspace_name, status, requested_at, due_at, completed_at, ready_at, expires_at, download_available, file_size, scheduled_for, error}`.

Export:
- `POST privacy/export` `{workspace_id?, password?}` (auth; needs a recent sign-in, see "Security rules") -> 201 request (200 when one is already running or ready). Without `workspace_id` it exports the caller's own data; with it the company's data, owner only (403 for admins and employees, 404 for strangers, 400 for personal workspaces). Limit 3 exports per user per 24 hours: 429 `export_limit`. Accounts up to `EXPORT_SYNC_MAX_CARDS` (15) cards and `EXPORT_SYNC_MAX_LEADS` (2000) leads are built while the request waits (status `ready` in the answer); bigger ones stay `pending` until the command `process_data_requests` builds them. Either way the signed link is e-mailed.
- `GET privacy/requests` (auth) -> `[request]` (newest first, the caller's own).
- `POST privacy/requests/{id}/download-link` (auth, own export only) -> `{url, expires_at}`: the same signed link as the e-mail, `<WEB_BASE_URL>/data-download/<token>`. 409 `download_unavailable` when not ready, used or expired.
- Body forms (the token stays out of the URL and the access log): `POST privacy/download/check` `{token}` and `POST privacy/download` `{token}` behave like the two routes below.
- `GET privacy/download/<token>/check` (no auth) -> `{valid, scope, expires_at, file_size}` without using the link up. `GET privacy/download/<token>` (no auth, throttle scope `data_download`) -> the ZIP as an attachment and the link is used up. Errors 410: `download_invalid`, `download_expired` (24 hours after the file was made), `download_used`. The e-mail points at a web page that calls `check` first and downloads on a button click, so link scanners in mail apps cannot use the link up.
- ZIP (user): `README.txt`, `profile.json`, `workspaces.json` (memberships), `cards.json` (every column of each card plus items, design, slug history, public URL), `leads.json` (leads of cards the user owns), `analytics.json` (anonymous totals and a per-day count), `audit.json` (entries by or about the user), `consents.json` (lead consent times, earlier data requests), `media/` (profile photo, card photos and covers, button icons, personal logos). ZIP (company): `README.txt`, `company.json`, `team.json`, `departments.json`, `cards.json`, `leads.json`, `analytics.json`, `activity_log.json`, `media/`. Password hashes, invite tokens and visitor hashes are never included. Files live in `EXPORT_ROOT` (private, never served as media) and are deleted by `cleanup_data_exports` once downloaded or expired.

Delete account:
- `POST privacy/delete-account` `{confirm: "DELETE", password | credential}` (auth) -> 202 request. `password` is the account password; accounts without one send a Google `credential` issued in the last 5 minutes for the linked Google account (else 400 on `password`, 401/403 Google errors). The account is disabled at once (existing tokens stop working), its cards are unpublished (those that were live are remembered), `scheduled_for` = now + 14 days (`DELETION_GRACE_DAYS`), and an e-mail with a restore link is sent. A company owner who owns a company with other people (any status) gets 409 `owns_company` with `fields.companies`; they must delete the company first (transfer of ownership is not built).
- While scheduled, `POST auth/login` with the right password answers 403 `account_scheduled_for_deletion` with `fields.restore_until`; a wrong password still answers 401 `invalid_credentials`. Google sign-in answers the same.
- `POST auth/restore` `{token}` (the e-mailed link) or `{email, password}` or `{credential}` -> `{user, access, refresh}`; cards that were live are published again; the request becomes `cancelled`; an e-mail confirms. 410 `restore_invalid` after the grace period, for a used link, or for an account that was not scheduled (a suspended account stays suspended).
- `purge_deleted_accounts` erases what is still scheduled when the date passes: the user row stays as an empty shell (so audit rows keep the actor id) with e-mail `deleted-<id>@deleted.invalid`, no name, photo, Google link or password; their cards are deleted with their files; their seats are removed; leads of company cards stay with the company (`card_id` null, `card_name` "Deleted card"); the personal workspace and any company they own alone are erased (invoices keep pointing at the emptied workspace row); audit rows lose `actor_name`, `actor_email` and member names; export files are deleted; a "your account was deleted" e-mail goes to the old address. Erasure refuses (and tries again next run) while the account still owns a company with other people.

Delete company (company workspaces, owner only):
- `POST privacy/workspaces/{id}/delete` `{confirm_name, password | credential}` (auth) -> 202 request. `confirm_name` must equal the company name exactly. Cards go offline at once, `GET workspaces/{id}` carries `deletion_due_at`, every non-owner route of the company answers 403 `workspace_pending_deletion`, the owner and the team get an e-mail (audit `company.deletion_requested`). 409 `already_scheduled` if already pending.
- `POST privacy/workspaces/{id}/restore` (owner) -> `{workspace_id, restored: true}` (cards that were live are published again, audit `company.deletion_cancelled`, e-mail). 410 `restore_invalid` once the date has passed.
- `purge_deleted_accounts` erases the team seats, cards, leads, departments, change requests, the audit log and the pictures, and empties the company row (name "Deleted company"); the invoices remain.

Commands to schedule: `process_data_requests` (every 5 minutes), `cleanup_data_exports` (hourly), `purge_deleted_accounts` (daily; `--dry-run` only counts). Settings: `EXPORT_ROOT`, `EXPORT_LINK_HOURS` (24), `EXPORT_DAILY_LIMIT` (3), `EXPORT_SYNC_MAX_CARDS`, `EXPORT_SYNC_MAX_LEADS`, `DELETION_GRACE_DAYS` (14), `DATA_REQUEST_DUE_DAYS` (30).

## Google Wallet pass
`GET cards/{id}/wallet/google` (auth; the card's owner, a manager of its workspace, or the employee it is assigned to; anyone else 404) -> `{save_url, warnings: [string]}`. `save_url` is `https://pay.google.com/gp/v/save/<jwt>`. Errors: 503 `wallet_not_configured` (issuer id, service account or key missing or unreadable; the web app then hides the button), 409 `card_not_published`, 402 `subscription_required` (plan not live).

The JWT is RS256, signed with the service account's private key, claims `{iss: <client_email>, aud: "google", typ: "savetowallet", iat, origins: [WEB_BASE_URL], payload: {genericClasses: [{id}], genericObjects: [object]}}`. Class and object are both embedded, so Google creates them when the person taps Save and no Wallet REST API call is made (Google calls this the "fat" JWT; the class id `<issuer>.<GOOGLE_WALLET_CLASS_SUFFIX>` is the same every time, so it is idempotent). Object id `<issuer>.<public_code>`. Object fields: `cardTitle` (company, else product name), `header` (name), `subheader` (job title), `hexBackgroundColor` (the card's own colour: the company palette `bg` for colourway 4, otherwise the `bg` of the face's colour set from `wallet/card_colours.json`, copied from the web library by `scripts/build_wallet_colours.py`; the brand ink colour for custom faces; always a valid `#RRGGBB` giving at least 4.5:1 with white text or 7:1 with black, darkened when needed), `logo` (company logo, else card photo, else the BENCH mark `/brand/icon-512.png`), no `heroImage` (the pass shows no banner picture), `barcode` QR with `<public_url>?s=qr` (so scans count as QR visits), `textModulesData` (phone, email, website, address, max 6) and `linksModuleData` (the card link plus http(s) buttons, max 6). Pictures must be public `https` URLs Google can load: other pictures are left out and named in `warnings` (so set `API_BASE_URL` to the public https host of the media). If the link would pass 3000 characters, address and links are dropped step by step.

Updates (Wallet REST API, setting `GOOGLE_WALLET_REST_UPDATES`, default on when the wallet is configured): when the link is asked for, the backend first stores the pass at Google with the same service account (OAuth token from a service-account JWT, scope `wallet_object.issuer`, kept in memory only; class `<issuer>.<GOOGLE_WALLET_CLASS_SUFFIX>` is created with just its id if missing; object created with POST, or updated with PATCH when it already exists) and returns a SHORT link whose JWT is `{payload: {genericClasses: [{id}], genericObjects: [{id: <object id>}]}}`, the pass itself being already at Google. The response shape `{save_url, warnings}` does not change. If the REST call fails for any reason (API off, 403, network, timeout) the link falls back to the whole pass inside the JWT as described above, so the button never breaks, and the reason is kept on the pass (`last_error`). With `GOOGLE_WALLET_REST_UPDATES=false` only the inline link is used and a saved pass is never refreshed.

Keeping a saved pass current: table `wallet_walletpass` (one row per card: object id, hash of the last pass sent, last sync time, `dirty`, `last_error`, `attempts`, `next_try_at`). Saving, publishing, unpublishing, suspending, deleting a card, changing its design, items or photo, or its company's brand or logo marks the row dirty (one cheap query that can never fail the edit). The job `manage.py sync_wallet_passes [--limit 100] [--budget 50]` (cron every 5 minutes, flock through run_job.sh) rebuilds each due pass and PATCHes it only when its hash changed (an unchanged pass is never sent again; every pass is also re-compared every `GOOGLE_WALLET_RECHECK_HOURS`, default 24). An unpublished or suspended card sets the pass `state` to `INACTIVE`, a deleted card to `EXPIRED` (the pass stays in the wallet); a 404 means nobody saved the pass, so it is only marked synced; 429, 5xx and network errors back off 1, 2, 4 ... minutes (max 6 hours) and are given up after `GOOGLE_WALLET_MAX_ATTEMPTS` (default 6), 4xx errors are given up at once, and a run stops after 3 failures in a row. Updates are silent; `GOOGLE_WALLET_NOTIFY_ON_UPDATE=true` adds a short "Card updated" message with `notifyPreference`. Only `oauth2.googleapis.com` and `walletobjects.googleapis.com` over https can be called (same checked transport as the CRM connectors, 10 s timeout, answer size capped). Hidden items and private notes are never in the pass (`build_object` only uses items that are on). Staff: `GET staff/system/jobs` also returns `wallet: {rest_updates, passes, waiting, failing, last_error, last_synced_at}`. Manual check of the real connection: `python scripts/wallet_rest_check.py` (prints status codes only). The Wallet console user needs Admin access and the Google Wallet API must be enabled in the Cloud project.

Environment: `GOOGLE_WALLET_ISSUER_ID`, `GOOGLE_WALLET_SERVICE_ACCOUNT_FILE` (path of the JSON key) or `GOOGLE_WALLET_SERVICE_ACCOUNT_JSON` (the JSON itself), optional `GOOGLE_WALLET_CLASS_SUFFIX` (default `bench_card`).

Owner setup:
1. Google Pay & Wallet Console (pay.google.com/business/console): create a business profile, open Google Wallet API, and copy the Issuer ID (a long number).
2. Google Cloud Console: pick a project, enable the "Google Wallet API", IAM and Admin, Service accounts, create one (any name), Keys, Add key, JSON. Download the file.
3. Back in the Wallet console, Google Wallet API, Manage, Users (or "Authorize service account"): add the service account e-mail (`...@...iam.gserviceaccount.com`) with the Developer role.
4. While the issuer is in demo mode only Google accounts listed under Test accounts (same page) can save passes. When ready, press Request publishing access (Google reviews it, usually a few days).
5. On the VPS put the JSON key where only the app can read it (for example `/etc/bench/wallet-service-account.json`, `chmod 600`) and add to the backend environment (`backend/.env` or the systemd `EnvironmentFile`): `GOOGLE_WALLET_ISSUER_ID=...` and `GOOGLE_WALLET_SERVICE_ACCOUNT_FILE=/etc/bench/wallet-service-account.json`. Restart the backend. Make sure `API_BASE_URL` is the public https address that serves the media files.

## Leads, analytics and reports
Added by migrations `leads.0005` and `analytics.0002` (run `migrate`). Company workspaces unless noted.

### Lead assignment, statuses, notes, timeline
Lead gains `assignee: {id, name, email}|null` (the company member it was given to), `assigned_at`, `consented_at`, `note_count`. Statuses are now `new`, `contacted`, `qualified`, `won`, `lost`. A lead stays with the company when its assignee is removed (`assignee` becomes null).
- Who sees what: owner and admin see every lead of the company. An employee sees the leads of their own card and the leads assigned to them. Anything else is 404.
- `GET workspaces/{id}/leads?card_id=&status=<one or a,b list>&source=&assignee=<member id>|me|none&from=YYYY-MM-DD&to=YYYY-MM-DD&q=&limit=50&offset=0` -> `{count, results: [Lead]}`. `me` and `none` are the "Mine" and "Unassigned" views. Dates are UTC days, both included.
- `GET workspaces/{id}/lead-assignees` (any member) -> `[{id, name, email, role}]`, the active members a lead can be given to.
- `GET leads/{id}` -> Lead plus `notes: [{id, author, body, created_at}]` and `activity: [{id, kind, actor, details, created_at}]` oldest first. `kind` is `created`, `assigned` (`details: {to, to_id, previous}`), `status_changed` (`{old, new}`), `note_added`, `emailed` (`{recipients}` for the card holder mail, `{to, reason: "assigned"}` for the assignee mail).
- `PATCH leads/{id}` `{status?, assignee_id?}` (at least one) -> the detail shape. `assignee_id: null` unassigns. Only owner and admin may send `assignee_id` (403 otherwise); it must be an active member of this company (400 `validation_error` on `assignee_id` otherwise) and leads of personal workspaces cannot be assigned (400). A change to the same value writes nothing. Assigning e-mails the new assignee (not when they assign to themselves).
- `POST leads/{id}/notes` `{body}` (1 to 2000 characters) -> 201 `{id, author, body, created_at}`. Internal notes are never shown to the visitor and never sent through webhooks.
- `POST workspaces/{id}/leads/bulk` `{action: "assign"|"status", ids: [..<=200], assignee_id?|status?}` -> `{action, total, ok, failed, results: [{id, name, ok, reason|null, code|null}]}`. Items are independent (ids the caller cannot see are `not_found`). `assign` is owner and admin only (403 for the whole call). A bulk assignment sends one summary e-mail to the assignee and writes one audit entry (`lead.bulk_updated`).
- Audit actions added: `lead.assigned`, `lead.status_changed`, `lead.bulk_updated`, `webhook.created`, `webhook.updated`, `webhook.deleted`, `webhook.secret_rotated`.
- `GET workspaces/{id}/leads.csv` takes the same filters. Columns: `created_at, card, name, email, phone, company, note, source, status, meeting_times, id, channel, assignee, assignee_email, consent (yes|no), consented_at`, then `internal_notes` when `notes=1` (owner and admin only, else 403), then `tag` (event mode: hot, warm, follow_up or empty) and `event_name`. The last two are always the final columns, so the earlier columns keep their places; `source` is the column named `source` (link, qr, nfc, event, ...) and the phone's own `client_ref` is not exported. UTF-8 with a byte-order mark; a cell that starts with `= + - @` (or a tab or return) gets a leading apostrophe. The file is streamed, holds at most 50000 rows (`LEADS_CSV_MAX_ROWS`; header `X-Rows-Truncated: 1` when cut) and every download is an audit entry `lead.exported` `{rows, notes, truncated, filters}`.
- `GET workspaces/{id}/lead-assignees` is owner and admin only. While a company is scheduled for deletion every contact route (list, detail, notes, bulk, assignees, add, webhook delivery log) answers 403 `workspace_pending_deletion`; only the owner can still download `leads.csv`. Webhook events are not sent during that time and go out again if the company is restored.

### New-contacts bell
Added by migration `leads.0007` (run `migrate`). Both routes follow the contact rules above (404 for a non-member, 403 `workspace_suspended` and `workspace_pending_deletion`, for every role).
- `GET workspaces/{id}/lead-bell` -> `{unread: int, latest: [{id, name, card_name, source, created_at, kind: "contact"|"meeting_request"}]}`. `latest` holds at most 5 contacts, newest first. Only contacts this person may see (same rules as the contacts list) that arrived after their own last-seen time count; a person who never looked sees the last 30 days at most, and an old last-seen time never reaches back further than 30 days. Contacts the person saved by hand (`scanned_card`, `event`) are not counted. `kind` is `meeting_request` when the source is `meeting_request`, else `contact`.
- `POST workspaces/{id}/lead-bell/seen` -> 204. Sets this person's last-seen time in this workspace to now (stored per person and workspace in `LeadSeen`); other people's counts do not change.

### Webhooks (owner and admin)
`WebhookEndpoint`: `{id, name, url, events: ["lead.created"|"lead.updated"|"lead.assigned"], enabled, secret_hint: "...abcd", consecutive_failures, disabled_reason, last_success_at, last_failure_at, created_at}`; the full `secret` (`whsec_...`) is in the answer that creates the endpoint or makes a new secret, and never again.
- `GET workspaces/{id}/webhooks` -> `{events: [all event names], results: [WebhookEndpoint]}`; `POST workspaces/{id}/webhooks` `{url, name?, events?}` (default all events; up to 10 per company) -> 201 with `secret`; `GET|PATCH|DELETE workspaces/{id}/webhooks/{wid}` (PATCH `{url?, name?, events?, enabled?}`; switching on clears the failure count); `POST .../{wid}/secret` -> new secret (the old one stops working at once); `POST .../{wid}/test` sends a sample `lead.test` event right now and answers the delivery with `response_body` and `payload`; `GET .../{wid}/deliveries?status=&limit=30` -> `{count, results: [{id, event_id, event_type, status: pending|success|failed, attempts, response_status, error, duration_ms, is_test, next_attempt_at, created_at, delivered_at}]}`; `GET .../deliveries/{did}` adds `response_body` and `payload`.
- Address rules (400 `validation_error` on `url`): https only, no user name or password, the name is looked up and every address it points to must be public (loopback, private, link-local including the 169.254.169.254 metadata address, shared 100.64/10, multicast and reserved ranges, and IPv6 equivalents are refused). The check runs again at every send and the connection goes to the checked address. Redirects are not followed, the wait is 5 seconds, only the first 1000 characters of the answer are kept. The development switch `WEBHOOK_ALLOW_PRIVATE_TARGETS=1` (environment or setting) allows http and private addresses; never set it in production.
- Message: `POST` with a JSON body `{id, type, created_at, workspace_id, data: {lead: {id, name, email, phone, company, message, source, channel, status, meeting_times, card_id, card_name, assignee: {id, name, email}|null, consent: {given, at}, created_at}}}`; `lead.updated` adds `data.changes: {status: {from, to}}`, `lead.assigned` adds `data.previous_assignee`. Headers: `X-BENCH-Signature: sha256=<hex>` = HMAC-SHA256 of `<timestamp>.<raw body>` with the endpoint secret, `X-BENCH-Timestamp` (seconds since 1970), `X-BENCH-Event-Id` (the same on every retry) and `X-BENCH-Event`. A 2xx answer is success.
- Queue: events are written to a database queue when they happen and sent by the command `deliver_webhooks` (run every minute from cron; running it twice at once is safe because each delivery is claimed first; finished rows are deleted after 90 days). One run takes deliveries round-robin per endpoint (5 per endpoint, a time budget per endpoint and per run), so a slow receiver cannot hold up the others; every send has a 3 s connect limit and an 8 s total limit. Creating, enabling or testing an endpoint needs a live company plan (402 `subscription_required`) and no events are queued without one; the test button allows 5 a minute per endpoint (429). A failed send is retried after 1 min, 5 min, 30 min, 2 h, 6 h, 12 h and 24 h (8 tries in all). 20 failed sends in a row switch the endpoint off (`disabled_reason` set) and e-mail the owner and admins; any success resets the count. Test events do not count.

### Analytics by person, department, link and source
All routes take `days=N` (1 to 365, default 30) or `from=YYYY-MM-DD&to=YYYY-MM-DD` (both included, at most 365 days), and `tz=<IANA name>` (default UTC). Days are cut in that zone, so a company-wide zone setting is not needed; the web app sends the viewer's zone. The previous period is the same number of days right before the range. Every answer has `period: {from, to, days, prev_from, tz, group?}`. Employees only ever see their own cards' numbers; the overview, people, links and sources routes accept `card_id=`.
- `GET workspaces/{id}/analytics` keeps its shape (see Analytics) and gains `group=day|week|month` (series buckets: the day, the Monday of the week, the first of the month; empty buckets are zero), `tz`, `from`/`to`, `period`, and `series[].link_clicks`.
- `GET workspaces/{id}/analytics/people?by=person|card` -> `{period, by, rows: [{key, member_id|null, name, person, department_id|null, department|null, cards, card_ids, totals: Metrics, prev: Metrics}], totals, prev_totals}`; `Metrics = {views, scans, taps, saves, link_clicks, leads, won}`; rows are sorted by views.
- `GET workspaces/{id}/analytics/departments` (owner and admin, else 403) -> `{period, rows: [{id|null, name, people, cards, totals, prev, top_person: {name, views}|null}], totals, prev_totals}`; every department is listed, plus "No department" when someone without one has a card.
- `GET workspaces/{id}/analytics/links` -> `{period, rows: [{kind, clicks, prev_clicks, visitors, share, top_card: {name, clicks}|null}], total, prev_total}`, the button leaderboard.
- `GET workspaces/{id}/analytics/sources?group=` -> `{period, rows: [{key: qr|nfc|link|email|other, views, prev_views, saves, leads, share}], total, series: [{date, views, saves, link_clicks, leads, qr, nfc, link, email, other}]}`. `leads` per source are counted by the lead's `channel`. A card link opened from an NFC tag counts as `nfc`; "shared" links are `email` (the share link) and `link` (a direct link).

### Weekly report
A week is an ISO week (Monday to Sunday, UTC); the report covers the last full week and compares with the week before. People get the report of their own cards (numbers: views, scans, saves, link clicks, new leads, won leads, most used button, change against the week before); owners and admins of a company also get the company report (totals, top 5 people, leads by status, open leads nobody owns, changes waiting for approval). Both default to on.
- `GET|PATCH workspaces/{id}/report-preferences` (any member) `{personal_report, company_report|null, can_company_report}`; `company_report` is only for owner and admin of a company (others get 403 when they try to set it).
- `GET workspaces/{id}/reports/weekly/preview?kind=personal|company&week=last|current` -> `{kind, week: {year, week, from, to, partial}, subject, html, text, data}`; nothing is sent and the e-mail has no unsubscribe link in the preview. `kind=company` is owner and admin only (403).
- `GET reports/unsubscribe?token=` (no sign-in) switches that report off for that person and workspace and shows a small page with an Undo button (a POST with `token` and `resubscribe=1`). A POST with the token (the mail header `List-Unsubscribe-Post: List-Unsubscribe=One-Click`) unsubscribes without a page. Tokens are signed and carry the user, the workspace and the kind (`personal` or `company`); a bad token shows a plain "link not valid" page and changes nothing.
- Command `send_weekly_reports [--dry-run] [--week 2026-W46] [--only personal|company] [--batch-size 200]`: run once a week (Monday morning, UTC) from cron. A sent-log row per person, workspace, kind and ISO week makes a second run send nothing; a failed send frees its row so the next run retries. People with no card, or with no activity in either week, get no personal report. Needs `API_BASE_URL` (the unsubscribe link is built from it).

## Guide progress (getting-started guides, prompts, help feedback)
What a signed-in person did with the in-app guides. Whether a checklist step is really done is worked out in the web app from live data; these rows only hold what data cannot show. Every row belongs to one person and is never visible to anyone else.
- `GET guide/progress` -> `{items: [{guide_id, step_id, state, updated}]}` (the person's rows, at most 600).
- `PUT guide/progress` with `{guide_id, step_id, state}` or `{items: [{...}, ...]}` (1 to 20 entries) saves rows (one row per person, `guide_id` and `step_id`; a later save replaces the state) and answers `{items: [saved rows]}`. State `reset` deletes the row instead.
- `guide_id` and `step_id`: 1 to 64 characters, lower-case letters, digits, `_ . : -`, starting with a letter or digit. `state`: `done`, `skipped`, `dismissed`, `shown`, `up`, `down`, or `reset`.
- Errors: 401 without sign-in. 400 `validation_error` (with `fields.guide_id`, `fields.step_id`, `fields.state`, or `fields.items` for a list that is empty, not a list or over 20 entries). 400 `guide_limit` when a person already holds 600 rows and adds a new one (changing an existing row still works). Messages are translated by exact English wording (see Languages); the web app shows its own texts by `code`.
- How the web app uses the rows: `welcome/seen` (the welcome was shown or skipped), `welcome/audience-<personal|company_owner|employee>` = `done` (what the person said they want to do), `checklist/hidden` = `dismissed`, `<audience>/<step id>` = `done` or `skipped` (a step ticked or skipped by hand), `flag/<name>` = `done` (things only the browser saw, such as `shared_qr_opened` and `signature_copied`), `next/<event>` = `shown` (a "what next" prompt was shown, so it is never shown twice), `help/<article slug>` = `up` or `down` (the "Was this helpful?" thumbs).

## Languages (Arabic and right to left)
Supported codes: `en` (the source language, the default) and `ar` (Modern Standard Arabic, right to left). More are added in one place (see the README, "Languages").
- User: `language` (`"en" | "ar" | null`, null until chosen) is returned by every user object (`auth/me`, login, register). `PATCH auth/me {language}` saves it; `""` or `null` clears it; any other value is 400 `validation_error` with `fields.language`. `POST auth/register` takes an optional `language` (same values; also taken from the `X-Language` header when the body has none). The language of an account decides the language of every e-mail it receives (reset, data export, deletion and restore, approvals, lead and assignment notices, webhook switched off, the weekly reports).
- Request language for API messages: the `X-Language` header, then the signed-in user's language, then `Accept-Language`, then English. Error `message` and `fields` texts are translated by exact English wording (a text without a translation stays English); `code` never changes. CORS allows `Accept-Language` and `X-Language`.
- Card: `language` (`"en" | "ar" | "auto"`, default `auto`) is read and written like any card field (400 `validation_error` on another value) and is returned by `GET public/cards/<key>` inside `card`. `en` and `ar` fix the language and direction of the public page; `auto` follows the visitor (their choice, then browser), and for a visitor with neither it follows the card's own text (mostly Arabic letters gives Arabic).
- Invites: `POST workspaces/{id}/invites` entries take `language` (`""`, `en`, `ar`); the invite e-mail is sent in it, `GET invites/{token}` returns it as `language` (or null), and accepting the invite gives the new account that language when it has none.
- vCard (`GET public/cards/<key>/vcard`): UTF-8 (`text/vcard; charset=utf-8`), vCard 3.0. Text properties whose value is outside the Latin alphabet (Arabic names, titles, companies, addresses) are written with `;CHARSET=UTF-8` (`FN;CHARSET=UTF-8:...`) for older contact apps. Names are never transliterated. `N` takes the last word as the family name, together with a preceding "Al", "El", "آل" or "ال" when a given name stays in front.
- E-mails: `lang="ar" dir="rtl"`, right-aligned, an Arabic-capable font stack, Latin names isolated with Unicode isolates inside Arabic sentences, dates with Arabic month names (Western digits), counts with the six Arabic plural forms.


## Staff area and custom designs

Staff API under `/api/v1/staff/`. A person without a staff role gets 404 on every staff route (the area is not revealed). Roles are stored in `User.staff_role` (`none`, `read_only`, `support`, `admin`). Every staff route also needs the second step: the header `X-Staff-Token` from `/staff/verify` or `/staff/totp/confirm` (valid 12 hours, revoked by logout, demotion or an admin reset). Without it: 403 `staff_verification_required`. `/staff/me`, `/staff/totp/*`, `/staff/verify` and `/staff/logout` need only the sign-in.

Role matrix (GET = read, other methods = write):

| Action | read_only | support | admin |
|---|---|---|---|
| Read requests, faces, companies, audit log, staff list, starters | yes | yes | yes |
| Own security: enrol, recovery codes, logout, sanitiser dry run | yes | yes | yes |
| Requests: reply, internal note, status change, assign, upload files | no | yes | yes |
| Faces: create, save, versions, restore, send for review, preview links, publish, disable, enable | no | no | yes |
| Staff roles: grant, change, remove, reset someone's two-step | no | no | yes |

At least one admin must remain (409 `last_admin`). The first admin is named with `python manage.py grant_staff <email> admin`.

Two-step (TOTP, RFC 6238, SHA1, 6 digits, 30 s, one step of drift, a used code is refused): `POST staff/totp/enrol` returns `{secret, otpauth_uri, qr_payload}` (409 `already_enrolled` once confirmed); `POST staff/totp/confirm {code}` returns `{recovery_codes[10], token, expires_at}`; `POST staff/verify {code}` or `{recovery_code}` returns `{token, expires_at}`; `POST staff/recovery-codes` renews the ten codes (stored as hashes, each works once). Five wrong codes lock the account for 15 minutes (429 `staff_locked`); the verify routes are also throttled per person (`user_sensitive`).

Staff audit log: `GET staff/audit?actor=&action=&q=&page=` (append-only rows: who, role, action, target, time, hash of the address). Companies: `GET staff/companies?q=` (name, plan, seats, status, owner, open requests). Requests: `staff/design-requests` (board, filters `status`, `assignee`, `q`), `<id>`, `/messages`, `/files`, `/status`, `/assign`, `/faces`. Faces: `staff/faces/<id>` GET and PATCH, `/versions`, `/versions/<n>/restore`, `/send-for-review`, `/previews`, `/previews/<pid>/revoke`, `/publish`, `/disable`, `/enable`, `staff/faces/sanitize` (dry run), `staff/starters`.

Company side (owner or admin of a company workspace; others 404 or 403), under `workspaces/<id>/`: `design-requests` GET list and POST create (409 `request_open` while one is open), `design-requests/summary`, `design-requests/<rid>` GET, `/seen`, `/messages {body,file_ids}`, `/files` (multipart `file`; png, jpg, webp or pdf by magic bytes, 10 MB, 10 per request), `/files/<fid>/download` (authenticated, `nosniff`, never public), `/withdraw`, `/approve`, `/request-changes {comment}`, `/preview`; `custom-faces` (live or approved faces of this company, readable by every member). Statuses: new, contacted, in_design, in_review, changes_requested, approved, live, closed, withdrawn; open means all but live, closed and withdrawn.

Public: `GET public/custom-previews/<token>` (no sign-in; token hashed in the database, 30 days, revocable, `noindex`).

Design key `design.custom_face`: `null` or a face id. It is accepted only for a face of the same company with status `approved` or `live` (400 otherwise, also for personal workspaces) and is covered by the company lock and department overrides (a department that picks a standard `face` without `custom_face` clears it). New codes: `request_open`, `request_finished`, `not_in_review`, `bad_transition`, `no_face_in_review`, `not_approved`, `bad_state`, `face_empty`, `face_palettes`, `last_admin`, `already_enrolled`, `totp_not_enrolled`, `staff_locked`, `staff_verification_required`. Their Arabic is in `backend/ilaf/locale_ar_designs.py`; the web words them by code (`designs.err.*`). Sanitiser warnings are `{where, code, message, count, params}`; the web words them from the code (`staff.warn.*`).

### Template language of a custom face

HTML subset: `div span p i b small br img` and `svg g defs path rect circle ellipse line polyline polygon linearGradient radialGradient stop clipPath mask`. Only `class` (and on `img` `src alt width height`, on SVG the drawing attributes) survive; no `style`, no events, no links, ids only on SVG gradients, clips and masks. `img src` must be `data:image/(png|jpeg|webp|gif)` or one of the company's own uploaded files. Placeholders: `{{name}} {{first}} {{last}} {{title}} {{company}} {{address}} {{phone}} {{email}} {{web}} {{initials}}` (escaped text), `{{photo}}` (the engine's `.pic`: the photo, or the initials when the photo is off), `{{qr}}`, `{{logo}}`, `{{symbol}}` (an `img.cfm`), `{{phone_line}} {{email_line}} {{web_line}} {{address_line}} {{lines}}` (the engine's `.ln` lines with icon). Conditionals: `{{#if photo}}..{{else}}..{{/if}}` on any placeholder name (true when the value exists), balanced inside the same element. Use the engine classes `n` (name), `t1` (title), `cl` (contact lines), `ln`, `pw` (photo box) so name fitting, the font and size choices and the company logo corner logic keep working. A template that uses `{{logo}}` or `{{symbol}}` gets no automatic corner logo. Three starter templates (clean left aligned, centred monogram, split colour block) are in `backend/designs/starters.py`.

CSS subset: classes, simple tags, `:first-child`, `:last-child`, `:nth-child()`, `:not(.x)`, `::before` and `::after`, `:scope` (the face itself); every selector is scoped to `.cfl .face.cf-<id>`. Whitelisted properties only (layout, box, colour, typography, background, border, shadow, transform, `clip-path`, limited `filter`, animation). Sizes in `cqw`, `%` and `em` (no px, vw, vh). Colours, gradients, `var(--cbg|--cbg2|--cfg|--cacc|--con)`. `url()` only for `data:image/*` (200 KB in total) and the company's own files. `@keyframes` names must start with `cf<id>-`; animations are at most 5 s and never infinite. No `@import`, `@font-face`, `@media`, custom properties, `!important`, `content:url()`. Limits: template 60 KB, CSS 120 KB (embedded pictures count separately).

## Support (tickets, e-mail replies, live chat)

App `support`. Tickets are numbered `PREFIX-00001` (`SUPPORT_TICKET_PREFIX`, default `BNC`). Answers are localised by `X-Language` like every other error. Staff endpoints use the staff guards (role matrix below, second step `X-Staff-Token`) and write the staff audit log.

**Customer (signed in)**
- `GET /support/summary` -> `{unread, open}`. `GET /support/tickets?status=open|solved|closed` -> own tickets (never merged ones). `POST /support/tickets` (JSON, or multipart with `files`, max 5, each PNG/JPG/WebP/PDF/TXT/LOG up to 10 MB, checked by their bytes): `category` (`account billing cards_design team_company bug feature_request privacy_data other`), `subject` (200), `body` (10000), `include_context` (default true), `context` (object or JSON string; only `page_url`/`route` (path only), `app_language`, `build_id`, `screen {w,h}`, `card_id`, `workspace_id` are read; anything that looks like a secret is dropped; browser and OS come from the User-Agent; `role` and plan come from the server and only for a workspace the person belongs to), `workspace_id`.
- `GET /support/tickets/{id}` (messages without internal notes, `context`, `unread`, `can_reopen`, `reopen_until`, `active_chat_id`), `POST .../seen`, `POST .../messages` (`body`, `files`; reopens a waiting or recently solved ticket), `POST .../solve`, `POST .../reopen` (within 14 days of solving, else 409 `support_reopen_expired`), `POST .../rating` (`rating` 1-5, `comment`; only solved or closed), `GET .../files/{id}/download` (owner only; files of internal notes are 404).
- Someone else's ticket, message or file is always 404.

**Public**
- `GET /support/challenge` -> `{challenge, difficulty, min_wait}`: a signed, single-use challenge. `POST /support/contact`: `name`, `email`, `category`, `subject`, `body`, `challenge`, `counter` (a number such that `sha256("<challenge>:<counter>")` starts with `difficulty` zero hex digits), `website` (honeypot: must be empty), optional `context`. Signed-in callers skip the proof. The form must be at least `min_wait` seconds old. Throttle scope `support_public` (6/hour per address); blocked-word and banned-address checks apply. Answer `{number, label}`.
- `POST /support/inbound-email/` (header `X-Support-Secret`; 404 while `SUPPORT_INBOUND_SECRET` is empty, 403 when wrong): JSON `from`, `to`, `subject`, `text`, `html?`, `message-id`, `in-reply-to`, `references`, `headers` (object), `attachments` (`[{filename, content_type, content_base64?}]`; entries without content are only noted). Answer `{status: created|added|reopened|ignored, ticket, reason}`. The ticket is found by the number in the subject or in the To address, or by `Message-ID` / `References`; the sender must be the requester, otherwise a new ticket is opened. Auto-replies (`Auto-Submitted`, `Precedence`, `X-Auto-Response-Suppress`, `List-Id`, bounces, out-of-office subjects, our own address) are ignored; quoted text and signatures are cut; a mail is added at most once (by Message-ID).

**Live chat (signed in, or a signed-out visitor with the chat token in `X-Chat-Token`)**
- `GET /support/chat/status?workspace=` -> `{enabled, online, live, reason, in_business_hours, accept_seconds, signed_in, open_chat_id?}`. `enabled` is the support chat setting AND the `support_chat` feature switch for the company named by `workspace` (only a company the caller belongs to counts; without one the switch only matters when it is off for everybody). `online` (same as `live`) is true only when chat is enabled, the team is in business hours and somebody online has room: it is exactly what a new chat will get. `reason` is `online`, `switched_off`, `closed` or `nobody_online`. The web launcher uses these fields, so screen and server agree. A switch only stops NEW live chats: a chat that is already running (`active`) may finish; a `waiting` chat becomes a ticket when its switch goes off.
- `POST /support/chat/start`: `message`, `context`, and `name` + `email` when signed out. 201 with `{id, status, token?, converted_to_ticket, reason}` (send `context.workspace_id` so the company's `support_chat` switch applies). With nobody to answer (chat switched off in support settings or by the feature switch, outside business hours, nobody online) the message becomes a ticket at once: `status: offline_converted`, `converted_to_ticket: true`, `reason`, `ticket`, `auto_reply`. Errors: 409 `support_chat_open_exists` (one open chat per person or address), 409 `support_chat_offline` (offline and no message), 409 `support_chat_disabled`, 403 `support_banned`.
- `GET /support/chat/{id}/messages?since=<last message id>` -> `{messages, status, typing, read_id, staff_name, ticket?}` with an `ETag` (send `If-None-Match`: 304 when nothing changed). `POST .../messages` (`body` up to 2000, or multipart `files`), `POST .../typing`, `POST .../end`, `GET .../files/{id}/download`. Status values: `waiting active ended offline_converted`. A chat nobody accepts within `chat_accept_seconds` (default 120), or when staff go offline, becomes a ticket (`offline_converted`) and the customer is e-mailed; ending a chat e-mails the transcript and adds it to a ticket.

**Staff** (`/staff/support/...`; read-only staff may read, `support` and `admin` may change, `admin` alone edits settings, canned replies and bans)
- `GET tickets` (filters `tab=mine|unassigned|open|solved`, `status priority category channel workspace assignee(none|id) sla(ok|at_risk|breached|paused|done) from to q`, `page page_size`; with `counts` and `agents`), `GET tickets.csv` (support/admin; formulas neutralised; audited), `GET/PATCH tickets/{id}` (`status priority category assigned_to spam`), `POST tickets/{id}/reply` (`body` or `canned_id`, `internal`, `status`, multipart `files`), `POST tickets/{id}/merge` (`into`), `POST tickets/{id}/start-chat`, `POST tickets/bulk` (`ids`, `action assign|status|priority|merge`, `value`), `GET tickets/{id}/files/{id}/download`.
- `GET alerts` (every staff role, second step required; the counters behind the bell in the staff top bar) -> `{new_tickets, customer_replies, chats_waiting, total, latest: [{id, kind: ticket|reply|chat, label, requester_name, subject, created_at}]}` (`latest` is the 6 newest across the three kinds). `new_tickets`: status `new`, no staff reply yet, nobody assigned. `customer_replies`: open, new or waiting requests that were answered before and whose latest non-internal message is the customer's. `chats_waiting`: live chats still `waiting` or `active` whose latest real message (not a system line) is the visitor's. Merged and spam requests are not counted; internal notes never count. For `chat` items `id` is the chat id and `label` is empty; for the others `id` is the request id and `label` is the request number such as `BNC-00012`.
- `GET agents`, `GET/POST canned`, `PUT/DELETE canned/{id}` (placeholders `{name} {ticket} {agent} {product}`, English and Arabic bodies), `GET metrics?days=30`, `GET/PUT settings`, `GET/POST bans`, `DELETE bans/{id}`.
- Chat console: `GET chats`, `GET chats/{id}?since=`, `POST chats/{id}/accept|messages|typing|transfer|end|convert`, `GET chats/{id}/files/{id}/download`, `GET/POST presence` (`status` online/away/offline, `capacity`), `POST presence/heartbeat` (a person with no heartbeat for 5 minutes goes away).
- Audit actions: `support.ticket.{status,priority,category,assigned_to,spam,reply,note,merge}`, `support.bulk.*`, `support.chat.{accept,transfer,convert,end,start}`, `support.settings`, `support.canned.*`, `support.ban`, `support.unban`, `support.export`.
- Error codes (customer wording, English and Arabic): `support_blocked_content support_banned support_ticket_closed support_reopen_expired support_not_solved support_proof_failed support_chat_disabled support_chat_open_exists support_chat_offline support_chat_ended`; staff: `support_secret_invalid support_merge_mismatch support_chat_taken support_chat_not_yours support_chat_needs_account`.
- Jobs: `manage.py fetch_support_mail` (IMAP, every minute) and `manage.py support_tick` (every minute).

## Account security, devices, company trust, notifications and several cards
**2-step verification (any account).** `GET auth/2fa` (status: `enabled`, `required`, `recovery_codes_left`, `trusted_devices`), `POST auth/2fa/setup` (needs a recent sign-in or `password`; answers `secret` and `otpauth_uri`), `POST auth/2fa/confirm {code}` (answers ten `recovery_codes`, shown once), `POST auth/2fa/recovery-codes {code}` (new codes), `POST auth/2fa/disable {password|credential, code|recovery_code}`.
Sign-in: `POST auth/login`, `auth/google`, `auth/restore` and `invites/accept` answer `200 {mfa_required: true, mfa_token, methods}` instead of tokens when the account has 2-step verification (a remembered browser sends `device_token` in the body and skips the step). The second step is `POST auth/login/mfa {mfa_token, code | recovery_code, remember_device?}`; it answers like a finished login and, with `remember_device`, a `device_token` valid for 30 days (only its hash is stored). `mfa_token` is signed and lives 5 minutes. Five wrong codes lock the check for 15 minutes (`two_factor_locked`).
Company rule: `PATCH workspaces/<id> {"security": {"require_2fa": true}}` (owner only, owner needs it first). Members have 7 days; `GET auth/me` then carries `two_factor.required {workspace_id, workspace_name, deadline, enforced}`. After the deadline workspace routes answer 403 `two_factor_required`; `auth/*`, `me/workspaces` and the security routes stay open.
**Signed-in devices.** Every sign-in is a row (`auth/devices`): `GET` lists `sessions` (label such as "Chrome on Windows", masked address `203.0.113.x`, country when the proxy sends one, created and last used, `current`), `trusted_devices` and `events`; `DELETE auth/devices/<id>` signs one other device out; `POST auth/devices/sign-out-others`; `DELETE auth/trusted-devices/<id>`. Tokens carry the session id as claim `sid`. The web server forwards the visitor's browser as `X-Client-User-Agent`. A sign-in from a kind of browser not seen before for that person sends a "new sign-in" e-mail once.
**Verified company domain.** `GET/POST workspaces/<id>/domains {domain, mailbox?}` (owner posts; a code and a link go to `admin@`, `postmaster@`, `webmaster@` or an address at the domain; instant when the owner's own verified address is at the domain; free-mail and disposable domains are refused), `POST workspaces/<id>/domains/<id>/verify {code}`, `DELETE workspaces/<id>/domains/<id>`, `POST domains/confirm {token}` (the e-mailed link, no sign-in). The workspace JSON carries `verified_domain`, the public card `brand.verified_domain` and the directory `company.verified_domain`; the workspace `security` block adds `require_2fa`, `reply_to_email`, `verified_domains` and `suggested_email_domains`.
**Company e-mails.** Invites and decisions sent by a company use its logo (https only), accent colour (white or ink text, at least 4.5 to 1, else the product orange), a "Company via Product" sender and an optional reply-to: `GET/PATCH workspaces/<id>/email-settings {reply_to_email}`; `GET workspaces/<id>/email-preview?lang=en|ar` answers `{subject, html, from, reply_to}`.
**Notifications.** `GET/PATCH notifications/prefs` (`push_leads`, `push_support`, `daily_summary`, `timezone`; `vapid_public_key` is null while the server has no keys), `POST notifications/push/subscribe {endpoint, keys}`, `POST notifications/push/unsubscribe {endpoint}`, `POST notifications/push/test`, `GET|POST notifications/unsubscribe?token=` (daily summary, one click).
**Several cards.** Cards carry `label`, `sort_order` and `is_default`; `POST workspaces/<id>/cards/reorder {ids}`, `POST cards/<id>/make-default`, `PATCH cards/<id> {label, is_default}`. The plan limit (`plan_limit`) is unchanged.
**More button kinds.** `Document`, `DownloadFile`, `Menu`, `GoogleReview`, `Trustpilot`, `TripAdvisor`, `Vimeo`, `Loom`, `AppleMaps`, `WhatsAppChannel`, `Airbnb`, `Etsy`, `Shopify`, `Amazon`: https only, and the host must belong to the site (`Menu`, `Document` and `Shopify` take any https address). `POST cards/<id>/file` (multipart `file`) stores a PDF up to 10 MB (signature, no scripts, random name, five per card) and answers `{file_url}`, the value of a `DownloadFile` button; the public item then carries `download: true`.

## Error codes (every code the API answers)
The table is generated from `backend/ilaf/error_codes.py` (written by `python scripts/extract_error_codes.py` from the raising code; a backend test fails when it is out of date). A code never changes; the `message` is plain English by default and is translated by exact wording when the request language is Arabic (see Languages). Several codes (`validation_error`, `forbidden`, `not_found`, `plan_limit`, `subscription_required`, `field_locked`, `slug_taken`, `throttled`) carry different sentences for different causes; the table shows one example. `params` are the values a sentence may contain. `network_error`, `origin_refused` and the `invite_invalid`/`not_found` answers of the web app's own routes use the same shape.

The web app never shows the server's sentence directly: it shows the text of `apiError.<code>` in its own catalogue (English and Arabic, `web/src/lib/i18n/{en,ar}/apiError.ts`) through `apiErrorText`. A test checks every code here has both texts. Messages that travel inside a successful answer (`reason` of a refused item in a bulk run, the skipped rows of a team import) are translated by the API for the request language and shown only when they are in the page's language.
